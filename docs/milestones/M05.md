# M05 — Escalations, answer, allow, takeover

## 1. Identity

- **ID:** M05. **Objective:** Everything that needs a person reaches them and comes back. Every
  escalation class parks its lane or project and is rendered as the three-part message on the Mac;
  `baton answer` delivers a ruling flagless under the label; `baton allow` widens in place; a
  taken-over lane is handed back. After this milestone a night can end in a park that a person
  resolves with one command in the morning.
- **User-visible result:** An `asking` artifact stops its session, parks the lane, notifies the
  Mac with the question, its numbered options and the marked recommendation, and
  `baton answer M0n 1` resumes the session with the option's text under the ruling label.
  `baton answer` with two parked lanes of the same milestone name refuses and prints
  `<project>/<milestone>` candidates. `baton status` shows the parked lane and the verb.

## 2. Dependencies and entry conditions

M04 complete and installed; dispatched by the tick. The person still watches, for the last time:
the channel this milestone builds is what lets M06 run unattended.

## 7. Implementation checklist (ordered)

1. `escalate` and `resolve`, the events exactly as `docs/ARCHITECTURE.md` §6.2; every writer in
   M02–M04 that wrote an `escalation` directly now calls `escalate`.
2. `message_render`: address `<project> <milestone> · <class>`; content per class from
   `docs/SPEC.md` REQ-ESC-03 and the escalation table in "Where an escalation goes" §5; verb
   `baton answer <M> <n>`, `baton answer <M> "<ruling>"`, or the edit sentence. `notify` gets the
   address as title and the content as body.
3. `answer_resolve`: derivation 13; the long form `<project>/<milestone>`; refusal texts.
   `answer_deliver`: expand an option number to its text from the archived `asking` artifact;
   the ruling label with the question quoted and the time; `resume_session` with kind `ruling`;
   `resolution` with `how: ruling`. `"continue"` on a taken-over lane writes only the `resume`
   (the takeover releases by the rule).
4. `edit_reread_check`: for each parked lane, if the plan file's row or the brief's prompt differs
   from what was read at the escalation (compare a hash stored on the `escalation` event's
   `carries`), write `resolution` with `how: edit` and unpark. The `question` row transition writes
   `how: answered in place`.
5. `allow_write` per REQ-ESC-09; item 42 recorded from the docs as unknown and the `ask` refusal
   kept.
6. `prompt-lost`: a lane whose row went from `waiting` to stopped with no ruling delivered →
   notification once; the ruling that follows carries no dropped-call sentence.
7. The fixtures in §5, twice each.
8. Live, once, fixture project: a session parked on `AskUserQuestion`, left for the supervisor's
   idle window if the session allows (item 21); a `baton answer` end to end with the real binary.
9. `sh tests/run.sh`, `/review-2`, `/address`, completion evidence, the handover.

**Natural split point after item 4.** Escalations and `answer` exist; `allow` and `prompt-lost`
become `M05-b`.

## 9. Definition of done and evidence

Handoff per template with the test output, the live `answer` capture, `git log`, `git status`.

## 10. Risks and decisions this milestone settles

- **The edit re-read needs something to compare against.** The escalation's `carries` should hold
  the hash of the plan row and the brief prompt at the time; decide the exact fields here and
  record them.
- **A ruling never lands in a working session.** `answer` refuses a milestone that is not parked;
  do not weaken that for convenience.
- **The question is quoted in the label** because a session may have compacted since it asked.
- **`baton allow` discriminates by shape** if it ever reads a suggestion; today it takes only a
  typed rule.

## 11. Handoff and next milestone

watch.
