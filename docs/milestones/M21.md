# M21 — No false "Baton was not running" alarms

## 1. Identity

- **ID:** M21. **Objective:** a gap is reported only when Baton was in fact not running, and a reboot
  in the host's sleep history no longer makes every later gap "unknown".
- **User-visible result:** while ticks run, even slow ones, no `gap` message reaches the Mac; a
  reboot days ago does not turn the next real gap into a message the sleep history could have
  explained.
- **Size:** Small to Medium, about 2–3 hours including one measurement; high effort.

## 2. Dependencies and entry conditions

None in the plan. M20 (`lib/completion.sh`) and M19 (`lib/stops.sh`, `lib/derive.sh`) touch none of
this milestone's files. M15-b wrote `lib/host.sh`; read its completion evidence.

## 4. Requirements, scope, non-goals

**The measured finding.** After the reboot at 2026-10-01 15:36:04, thirteen `gap` notifications
reached the Mac by 18:35, each "no tick for 2 m … the sleep history could not explain it
(boot-boundary)", with `gap_seconds` 120 or 121. `~/.baton/launchd.err` shows why the gaps exist:
every other launchd run printed `lock held at …/lock (pid N, since T); nothing done`. Measured
18:31–18:35: the tick that took the lock at 18:31:41 wrote its marker at 18:32:49, and the one that
took it at 18:33:49 wrote its marker at 18:34:57: ticks of about 68 seconds on a 60-second schedule,
while a dispatched session's full `tests/run.sh` loaded the Mac (load average 4.4). Each tick started
60 seconds after the previous marker, on schedule, yet its gap event is stamped at its own end and
measures 120 seconds: the gap is read against a clock later than the one the tick started with,
which D-174 says it must not be. And every such gap was assessed `unknown` because `lib/host.sh`
prints `A boot-boundary` whenever the `Sleep/Wakes since boot` counter falls anywhere in
`pmset -g log`'s history (37,476 lines, weeks of it), with no timestamp to confine it to the window;
an unknown gap notifies.

**Scope.**

1. **Measure first.** Time each step of a tick under load, on a fixture home, with a `PS4`
   timestamp or per-step timing behind a test seam, and record which steps exceed a few seconds.
   If one step dominates and can be read once per tick instead of more often, do that; if the tick is
   simply near sixty seconds under load, say so with the numbers.
2. **The clock a gap is measured against.** A tick measures any gap against the instant it started
   (`tr_now`), on every path that writes a `gap` event, as D-174 requires; a tick that starts within
   two intervals of the last marker never reports a gap, however long it then runs.
3. **A skipped run is not an absence.** A scheduled run that finds the lock held by a live holder
   leaves a record that Baton was running, and the gap rule counts it, so a run of slow ticks never
   reads as Baton not running. Settle the record: a heartbeat file the lock-held exit writes
   atomically (never the log, which has one writer under the lock), or the holder's own start read
   from the lock.
4. **A reboot is confined to its window.** A `boot-boundary` makes a gap `unknown` only when the boot
   lies inside the window being assessed. Place each boot between the timestamped records around it,
   and use `sysctl kern.boottime` for the current boot; a boot outside the window is ignored.

**Non-goals.** No change to the gap threshold, to what an explained or unexplained gap means, or to
`HOST-EXPLAINED`'s silence. No new liveness probe, no model call, no second log writer.

## 8. Fixtures, verification, acceptance

Fixtures with a fixed clock, a `pmset` shim history and a held-lock fixture; run each twice and
`sh tests/run.sh`.

- Ticks of 68 s on a 60 s schedule, every other run finding the lock held, for ten intervals: no
  `gap` event.
- A tick that starts 60 s after the last marker and runs 70 s: no `gap` event.
- A sleep history with a reboot three days before the window and a sleep covering the window:
  `HOST-EXPLAINED`, silent.
- A reboot inside the window: `unknown`, one message, as today.

## 10. Risks and decisions this milestone settles

Counting a skipped run as "running" must not hide a tick that hangs forever: a holder that does not
answer is stale, as D-174 already separates, and a stale lock still reports. Record the decision at
the next free D-number read from `main` when it is written. Apply M19 §10, "Main advances while a
session runs", in full.
