## Acceptance

An actual authorized target run demonstrates identity-bound dispatch, usage interruption, one human ruling, verified integration and idempotent handover replay. Live checks are recorded passed/failed/unrun with captures. A missing live proof never becomes a successful acceptance claim.

Run sh tests/run.sh and add behavior assertions for the new transitions. Use fault injection at
new effect boundaries, not only snapshot comparisons. Use two independent reviews and address
concrete findings. No build, live session, launchd or target-project operation is implicit in the
fixture test suite. Obtain any required explicit authorization before a live acceptance action.

  beyond the saved checkpoint. Reconcile external state without duplicating the effect or
  inventing its acknowledgement. This is operating acceptance, not a new automatic restore command.
- Validate the journal's referenced artifacts/prompts/receipts and compatible release/configuration
  as one recovery unit. Missing/corrupt evidence remains explicit and the original is preserved.

  copy Baton's host-specific assumptions as proof that another project works.
- Keep unattended success, human-ruling delivery, exact integration and replay evidence separate.
  A completed night without observed outcomes does not satisfy version-1 acceptance.

## Recovery procedure

Inspect existing code, durable action records, candidate work and prior evidence. Resume only the
unfinished part. Do not reset failure budgets, duplicate external effects, overwrite human work,
or weaken an invariant to make a continuation succeed. Split scope into a real plan row if needed.
