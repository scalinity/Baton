# M20 — A rewritten history does not break a completion proof

## 1. Identity

- **ID:** M20. **Objective:** a completion whose recorded baseline was replaced by a history rewrite
  that kept every file identical is proved against that baseline's equivalent on the new history,
  instead of being rejected.
- **User-visible result:** after a message-only rewrite of a registered project's history, the
  lanes that were open across it complete and are consumed as usual; M15-c's parked handover,
  written again, is consumed.
- **Size:** Small, about 1–2 hours; high effort.

## 2. Dependencies and entry conditions

`lib/completion.sh` is a file neither of them nor M19 edits.

## 4. Requirements, scope, non-goals

**The measured finding.** At 2026-10-01 16:00:42 `main` in the canonical checkout was reset to
`origin/wip-sync/main`, a rewrite that removed `Co-Authored-By` and `Claude-Session` trailers from
commit messages. All 287 commits kept identical trees, authors and dates; only their ids changed.
Baton's log records each dispatch's baseline by commit id. M15-c's attempts 1 and 2 recorded
`a24b372f1f407cbeef2805b77fb498e29a8330f9`, which is no longer an ancestor of `main`; its rewritten
equivalent `3f0e0c78` has the same tree. `completion_baseline` returns the *first* baseline recorded
on the branch across attempts, so M15-c's attempt 3 handover (`merged_as`
`aed2d5efd52f194363692b6006f4918faf134e18`) was rejected at 17:11:31 with rule `completion-chain`
and the lane parked `other`. M15-e's attempt 1 recorded `e953bbbb1d9b2a5ad189ca2b8aa46ebc93f41c1d`,
also replaced, so its handover will meet the same rule. No route through the relay recovers either:
the log is append-only, a redispatch keeps the first baseline, and a handover written again is
judged the same way.

**Scope.**

1. **The equivalent baseline.** In `completion_baseline`, or where its result is used, a recorded
   baseline that is not an ancestor of the claimed `merged_as` is replaced by the ancestor of
   `merged_as` whose tree is identical to it, when exactly one such commit exists. A tree equal and
   an ancestor is the rewrite's own image of the commit Baton recorded, so the claim stays bound to
   what was dispatched and the measured range still covers every attempt's work.
2. **Otherwise as today.** No equivalent (the baseline object is gone, or no ancestor shares its
   tree, or more than one does): refuse with `completion-chain` as now, and say why in the detail.
   Never fall forward to a later attempt's baseline: that would shrink the range the proof measures.
3. **The record says so.** The completion evidence names the recorded baseline, the equivalent used
   and why, so a proof across a rewrite is distinguishable from an ordinary one.
4. **A handover written again is consumed.** A `complete` artifact rejected before this lands and
   written again by its session afterwards is judged anew and consumed; prove it, because M07-d's
   "acted on once" rules were written for consumed handovers, not rejected ones.
5. **A setup fact.** `docs/SPEC.md`'s setup facts gain one line: a rewrite of a registered project's
   history that changes file contents orphans the recorded baselines and is refused; one that keeps
   every tree is followed.

**Non-goals.** No rewriting of Baton's log. No change to what a completion must prove beyond the
baseline's identity. No change to the planning lane's branch reuse (a separate gap, owned by a later
milestone). No live session.

## Completion evidence

### 1. What changed

- **The equivalent baseline** (D-214). In `completion_chain`, a recorded baseline that is an ancestor of
  neither the branch tip nor `merged_as` is replaced by the one ancestor of `merged_as` whose tree is
  identical to it. A message-only rewrite keeps every tree and changes every id, so that ancestor is the
  recorded commit as the new history holds it. The range is measured from it: `changed_paths` is
  `git diff --name-only <equivalent> <tip>`, so the proof still covers every attempt's work.
- **Otherwise as before, with the reason.** No ancestor with the tree: the detail says so and gives the
  tree. Several: the detail says the equivalent is ambiguous and names the first three and the count.
  A baseline object that is gone, a history `git log` cannot read, and an equivalent the tip does not
  descend from each refuse `completion-chain` with their own detail. A later attempt's baseline is never
  substituted.
- **The record says so.** Only a proof that went through an equivalent carries `recorded_baseline` and
  `baseline_basis` beside `baseline`; they reach `chain.json`, `result.json` and the `consumed` event.
  An ordinary proof's document is unchanged byte for byte.
- **A rejected handover written again is consumed.** `completion-rejected-rewritten` holds the rejected
  copy in `rejected/` with its `rejected` and `escalation` events, then the same file written again:
  one `consumed` `complete`, the rejected copy left as the record. `repeat_of` only recognises consumed
  handovers, which is why a rejected one is judged anew.
- **A trigger narrower than the brief's.** The brief says "not an ancestor of the claimed `merged_as`".
  A baseline the tip descends from is not a lost commit, and the literal rule changed
  `completion-unrelated-ancestor`'s refusal (the tip is not inside the claimed merge). The equivalent is
  looked for only when the baseline is an ancestor of neither the tip nor the merge.
- **Review.** `/review-2` (two Opus reviewers) found no critical issues, four warnings and ten
  suggestions (one a duplicate, one noting nothing needed changing); all were addressed. The substantive ones: the `git log | awk` pipeline hid a read failure
  as "no equivalent"; two refusal branches had no scenario, and a mutation removing the merge half of the
  trigger passed the whole completion family; D-214 rested its safety on the wrong reason (see 6); and
  `completion_summary`'s cut, a pre-existing defect, tested bytes but sliced characters (see 7).

### 6. Known limitations

- **Twins on one ancestry line refuse.** A merge commit whose tree is its branch tip's, or an empty commit,
  beside the equivalent leaves two tree-identical ancestors and the detail says ambiguous, though either
  would give the same proof. `main` has twelve such pairs. A baseline taken at one of those merges
  refuses after a rewrite; close-out usually commits after the merge, so it is rare. Kept as decided.
- **The equivalent needs the baseline's own object**, because its tree is read from it. Once git prunes the
  unreachable commit, the baseline is refused as gone.
- **A coincidental tree twin** (an older state a revert restored) can stand in if the tip descends from it.
  That weakens the `B ⊂ T` ancestry check and nothing else, because `changed_paths` is a tree-to-tree
  diff; a range measured by commits would need D-214 reconsidered.
- Baton's log is not rewritten: a lane's recorded baseline stays the old id.

### 7. Deviations from the brief

- The trigger is narrower than "not an ancestor of the claimed `merged_as`" (D-214).
- `completion-wrong-baseline` changes: a baseline on no ancestor line whose tree no ancestor shares is the
  brief's no-equivalent case, so the two requirements "unchanged" and "the detail says no ancestor shares the
  tree" cannot both hold for it. Only that one line changed.
- Two scenarios beyond the four, and one fix beyond the brief's scope, `completion_summary`'s byte cut,
  because a reviewer found it and it sits in the same counted library. The brief's four scenarios are as
  named.
- Nothing was pushed: the branch's commits are local.
