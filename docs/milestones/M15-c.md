# M15-c — The independent scope guard

## 1. Identity

- **ID:** M15-c. **Objective:** always bring goal drift to the person through an independent check.
- **User-visible result:** a deliberately drifted milestone is stopped by a guard that knows
  the confirmed goal, not the plan's rationale. Aligned work advances without a routine human gate.
- **Size:** Medium, about 3–4 hours; high effort. This is M15's original natural split after replan.

## 2. Dependencies and entry conditions

M15-b complete and installed (and therefore M15/M12). Registration stores a confirmed goal;
completion records baseline, actual changes and Baton-produced standing-check evidence. Use
M15's human-required route and M12's adoption boundary. Read M13/M14's interfaces when available;
use the shared admission seam without adding entry dependencies.

## 3. Required reading

`CLAUDE.md`, `CONTEXT.md`, `CONTRACT.md`, `docs/MILESTONES.md`, SCOPE §6 M15 and §7;
SPEC §2.4, §2.5, §2.8, §2.9, §5; ARCHITECTURE §4.1–4.3, §5.2, §6.2, §6.4, §7, §10;
M12, M15 and M15-b completion evidence and decisions; current planning/adoption, completion,
escalation and CLI admission interfaces. Read M15's original finding for disposition boundaries.

## 4. Requirements, scope, non-goals

Independent goal-only checks before plan adoption and before each close-out advances successors.
Drift is always human-required and notifies. Neither AI resolution, replan nor HOST-EXPLAINED
can clear it automatically. No generic managed review framework, direct API call, new person
approval gate, inherited plan authority or replay of completed taxonomy/host work.

## 5. Expected files (proposed)

New `lib/scope.sh`; narrow planning/adoption and close-out integration seams;
`tests/scenarios/scope-guard-*`; SPEC, ARCHITECTURE §10, DECISIONS and this brief's evidence.
Inventory actual files first; more than two existing library edits requires another preimplementation
split per the plan. Outside the repository: CLI judgement prompts/results under existing state paths.

## 6. Interfaces

Independent goal-check request/result consuming only stored goal and proposed plan or actual
just-completed work/evidence. Use subscription CLI sessions via the shared admission seam and
existing records; explicit pass, drift or unresolved outcome. Missing/failed checks never pass.

## 7. Implementation checklist (ordered)

1. Establish an independent session context; verify that cwd, inherited instructions and sibling
   history cannot smuggle planning rationale or previous approval into the guard.
2. Before plan adoption, supply only goal and proposed plan; block advancement pending a result.
3. Before close-out advances successors, supply only goal and actual change/evidence; not the
   plan author's explanation. Make request/result consumption idempotent across ticks/restarts.
4. Route drift to a human-required escalation and Mac notification. AI/replan cannot approve or
   clear its own drift. Aligned work passes; unavailable/failed checks remain unresolved.
5. Run §8, document exact input isolation, review and close out.

## 8. Fixtures, verification, acceptance

- Fixture aligned/drifted plans and close-outs, failed/unavailable checks, exact input isolation,
  repeated ticks, and refusal of AI/replan/host disposition to clear drift; each twice, then
  `sh tests/run.sh`.
- Live: disposable fixture projects only, with aligned and deliberately drifted work checked in
  separate cold CLI sessions. Capture exact goal/work-only prompts and the drift Mac message.
- Acceptance: both boundaries checked independently; aligned work advances, drift reaches a
  person, unresolved checks block advancement, and the guard cannot approve its own escalation.

## 9. Definition of done and evidence

Ten-item handoff with exact guard input sidecars, isolation proof, fixture and live results,
human-directed drift record/message, and current boundary interfaces. Note any M13/M14 integration
proved only by fixture. Combined M15 acceptance is not complete until this part is done.

## Completion evidence
### 1. What changed

- **The scope guard exists, at both boundaries.** `lib/scope.sh` is the plan's second judgment
  session, on the reserved lane `M00-scope`, dispatched through `dispatch_one` — the shared admission
  seam — so the cap, the holds and M14's pacing admit it like any lane (`plan-generate-adopt` and the
  replan scenarios show the budget counting the guard as a session start). It answers one question,
  whether the work still serves the confirmed intent record, with a `verdict` of `pass` or `drift`
  and a `finding`.
- **Adoption waits for it.** `planning_adopt` asks `scope_adoption` at the line M12 marked; a plan
  that holds is adopted only on `pass` or on a person's answer to its drift, and meanwhile the
  verdict reads `waiting` so `planning_pass` commissions no second plan. A replanned plan (M15-d,
  merged on `main` during this milestone) reaches the same line and is guarded the same way.
- **Close-out waits for it without holding a slot.** `consume_settle` writes `scope: {request:
  "<milestone>-<attempt>"}` onto the `consumed` event of every proved completion, and `scope_hold`
  removes from the tick's candidates every milestone one of whose dependencies has a close-out
  request that is neither `pass` nor `released`. The completing lane closes exactly as before, so its
  slot is free before the guard needs one: the cap cannot deadlock on a guard (§4.5's rule).
- **Isolation is enforced and measured, not asked for.** The guard's input is its prompt alone —
  the confirmed intent record read at dispatch, and the work frozen when the request was made. It
  runs in a fresh directory per attempt under `checks/<project>/scope/<request>/`, which the deny
  rail already closes to every session; its settings deny `*`, switch off CLAUDE.md loading and
  auto-memory, and tell it its session id through a `UserPromptSubmit` hook; `claude_bg` launches it
  with `--setting-sources ''`, `--strict-mcp-config` and `--disable-slash-commands`; no slot line is
  composed. Not given: the brief, the plan's titles, commit messages, the generating session's
  prompt and transcript, any earlier verdict, any sibling.
- **Drift always reaches a person and nothing else clears it.** `drift` is a new escalation class,
  `human-required` as a constant on the class, so `record_only` refuses it whatever carries a caller
  attaches — a host explanation, options, its own answer written down, a replan flag
  (`disposition-silent-record`, `disposition-table`). No edit, replan or `done` releases it
  (`scope-guard-closeout-drift` commits a replan to `main` and the park and hold both stand). The
  one way out is `baton answer <project>/M00-scope "<ruling>"`, delivered to the guard's own session,
  stopped first so the resume is not a copy.
- **A check that did not happen is never a pass.** Owed, waiting, running, failed, unresolved and
  drift all hold. A guard that ends without a verdict is stopped and asked again by a fresh session,
  three per request, then the lane parks `other`; a registration with no confirmed intent fails at
  the prompt stage and parks `dispatch-failed` naming `baton onboard <path>`, released by the tick
  once the record exists; a guard stopped by an API error is waited out and resumed (`scope_waits`)
  rather than replaced under its own model hold; an unreadable verdict is rejected; a forged verdict
  is rejected.
- **The review brought nine changes**, each with a scenario: verdict provenance (the session must
  be a guard dispatch and the verdict must match the fence in its own transcript), drift outranking
  any later verdict, the hold reading every close-out of a dependency, the guard lane's waits, the
  bounded and fenced work (a hash-marked boundary and `| `-prefixed plan lines), a byte-cut drift
  park, delivered-only resumes, a launch-stage park left for a person, a stale candidate set aside, a
  guard the CLI will not stop parked once, `M00-scope` reserved in generated plans.

### 6. Known limitations

- **Baton's own registration has no confirmed intent record.** `install.sh` writes `{path, plan,
  check}` and M11 ran `baton onboard` on Baton only into a disposable home, so after this install
  each guarded close-out of a Baton milestone holds its successors and parks the guard lane
  `dispatch-failed` naming `baton onboard /Users/danny/Documents/Apps/Baton`. That is the guard
  doing its job — a check that cannot happen is not a pass (D-205) — and it is one confirmation,
  after which the park releases itself. **M16 is held behind M15-c's own close-out until then.**
- **Isolation flags are not re-applied on a resume.** Every resume is flagless and a flagless resume
  restores `-n`, `--effort`, `--permission-mode`, `--settings` and `--model` (D-080), so a guard
  resumed by a ruling or by the wait route keeps `deny: ["*"]` and the two env switches — they live in
  its settings file — but loads the user's settings sources, plugins and MCP servers. Its tools stay
  denied and CLAUDE.md stays off; what can reach it is plugin context such as a `SessionStart` hook.
  Deferred: the remedy is a fresh guard in place of a resume, which conflicts with the flagless-resume
  rule and with the ruling route that resumes the session it names.
- **[Pre-existing] The deny rail's Bash patterns are textual.** `cd ~/.baton; … > checks/…` does not
  match `Bash(*.baton/checks*)`, so a session determined to could rewrite a request's `work.txt`
  between the request and the dispatch. The prompt sidecar records what the guard was actually given.
  Deferred, because it is the rail's general limit (D-026), not the guard's.
- **[Pre-existing] A project whose key is `judge` shares `checks/judge` with onboarding's scratch,
  which `rm -rf`s it**; its requests rebuild from the log. Deferred with the rail item.
- **Provenance is tamper-evident, not tamper-proof.** A verdict must match the fence in the guard's
  own transcript, a file the same user can write.
- **One park on `M00-scope` holds every request of the project**: a drift on one close-out stalls the
  guards of unrelated close-outs and of a hand-repaired plan until a person answers it. The drift
  message says so.
- **A request that cannot be written** (repository gone, baseline unreachable) holds its successors
  with a line each tick and no park; the condition breaks the project's self-check too.
- **A finished guard is a finished session**, so guards count among the few most recent that
  `offline_check` keeps; frequent close-outs can take a milestone's finished session offline sooner.
- **`baton status` shows no held successors** — the tick's `held` lines go to launchd.out; status
  shows the guard lane in flight and any park on it.
- **[Pre-existing, found during the review fixes] The planning lane can hold a model for good.** A planning session in a project that owes a plan, stopped by a usage limit, leaves a wait that `stops_run` never resumes — that project never reaches it — so `holds_apply`'s hold on its model stands and `hold_bites` drops every candidate on that model in every project. The guard lane had the same defect and no longer has (D-210); the planning lane's remedy is the same `scope_waits` shape and belongs to a planning-lane fix.
- **The ladder's own `redispatch` still refuses a lane with no plan row**; the guard lane never
  reaches it because it is stood off, and the planning lane's analogous gap is M12's recorded one.
