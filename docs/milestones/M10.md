## 7. Implementation checklist (ordered)

1. Show the limitation with a fixture naming the repository's first commit as `merged_as`;
   keep a valid completion fixture beside it. Add a branch with no change in declared scope.
2. Require one bound chain: recorded attempt → dispatch baseline B → frozen candidate tip T →
   integration commit M (`merged_as`) → checked revision V. Resolve and record immutable commit
   identities: B from that attempt's dispatch, T from its recorded branch, and M from the claim.
   Require B to be an ancestor of T, T to be an ancestor of M, and M to be on main. Freeze T
   before deriving evidence; later branch movement must not substitute a different candidate.
   V must be M or a descendant of M on main, and the check result must name that exact revision.
   Reject a disconnected chain even when M descends from B and a separate branch has scoped work.

   on main; never inspect a moving branch independently to justify M. Settle how the declared

   actual result and output pointer with the same attempt/B/T/M evidence. Establish that the
   checked tree really is V; do not label an unverified or changing checkout with a sampled HEAD.
   A session-provided success string cannot satisfy this check. Preserve the
   existing broken-main behavior when the standing check fails.
5. Define the additive record enrichment and treatment of pre-M10 archived artifacts and already
   dispatched attempts. Keep repeat detection stable: re-delivery cannot dispatch or recheck twice
   just because Baton added evidence to the archived record.

## Completion evidence

### 1. What changed

- **A completion claim is now bound to the attempt Baton dispatched.** `merged_as_verify` asked
  only whether a hexadecimal value resolves to a commit ancestral to `main`; this repository's own
  first commit answers yes (L13). Four commits are now resolved to their immutable ids and four
  facts required of them: the attempt's baseline `B` from its own `dispatch` event, the frozen
  candidate `T` (the tip of that attempt's recorded branch, read once), the integration commit `M`
  (`merged_as`), and the checked revision `V` (`M`). `B` is an ancestor of `T`, `T` is an ancestor
  of `M`, `M` is on `main`, and the check names `V` exactly. The middle fact is the load-bearing
  one: ancestry from `B` to `M` alone is met by any old commit while the work sits elsewhere.
- **The changed paths come from that same frozen `T` against `B`** — `git diff --name-only B T`, the
  branch's own commits — so work that landed on `main` in parallel cannot stand in for this
  milestone's, and at least one changed path must fall inside the milestone's declared scope.
- **The declared scope is the brief's existing `## 5.` section**, read as its backticked path spans
  with `{a,b}` expanded and `*` read as a glob. Inclusion, not an allowlist: the heading says
  *proposed*, and requiring every changed path to be inside it would reject the ordinary close-out,
  which edits `docs/DECISIONS.md` and the plan file whatever the milestone was.
- **The check result is Baton's.** It checks out `V` detached under `$BATON_HOME`, requires the
  tree to report that revision and to be clean, runs the registration's `.check.command` under a
  deadline, and records the command, revision, exit status, outcome and output pointer. A session
  that writes its own `check_result` is rejected under the rule `reserved-field`.
- **A check that did not pass parks the project `main-broken`** — the existing broken-main ending,
  reached by Baton's own run rather than by the session's word for it. The handover is still
  consumed, because the work really did merge; the park is what stops the chain.
- **F07, first: a consumption whose receipt was lost is finished on a later tick.** `archive_move`
  precedes the `consumed` event, so a tick killed between them left a file in the archive that no
  event claimed — derivation 4 has named it under `unrecorded` since M02 and nothing acted on it.
  The inbox pass now writes that receipt, marked `reconciled`, before it looks at any inbox file,
  and applies the ending that consumption owed.
- **Every piece of evidence is produced before the move**, which is what makes an archived artifact
  a checked one by construction and lets the reconciliation be a receipt write rather than a second
  verification. The full evidence is written to
  `checks/<project>/<milestone>-<attempt>/result.json` before the move and read back from there.
- **Two completions are recorded unproved rather than rejected**: one with no recorded attempt (the
  hand-started bootstrap M01 still stands on) and one whose attempt was dispatched before the
  baseline was recorded. There is deliberately no fallback deriving the baseline from the
  repository: once the merge is on `main`, the branch's merge-base with `main` is the branch tip
  itself, so a guessed baseline would refuse honest work while looking like proof.

### 6b. What the review changed, and the two things it left

Both reviewers and the hand pass are dispositioned in `D-152`. Two findings are named and not
fixed, each for a stated reason rather than an oversight:

- **A standing check that holds the tick lock for minutes makes the gap rule report the check as an
  outage.** Verified in the code, not inferred: `derive_gap` measures `now − last-tick` at step 7,
  the marker is the previous tick's, and `dg_closed` counts the `consumed` event the same tick just
  wrote. So the first completion Baton proves with its own check sends a Mac message saying the
  relay was not running for the length of the check it was running. `lock_stale_report` separately
  advises that a lock held that long may be stale. Fixing either needs `lib/derive.sh`,
  `lib/rows.sh` and `lib/tick.sh` — three counted files against this milestone's budget of two, and
  the split rule triggers at three. **`M10-b` is written for it**, with a brief, a plan row
  depending on M10, and a note in the split-rule section saying it was split after implementation
  rather than before, because M10's own acceptance holds in full.
- **The deadline's kill reaches the subshell and its direct children.** `sh -c` execs a simple
  command, so the ordinary case is the check itself; a check that forks workers of its own can
  leave them behind after a timeout. A process-group kill needs job control in a non-interactive
  shell, which is a subtlety not worth introducing into the check runner for a leak that follows
  only a timeout.
