# M14 — Budget-aware pacing

## 1. Identity

- **ID:** M14. **Objective:** pace unattended work against the subscription allowance, pause
  cleanly before exhaustion and resume automatically when its window rolls.
- **User-visible result:** `baton status` shows a budget pause and resume time instead of an
  apparently working lane whose dispatch has failed on quota.
- **Size:** Medium, about 3–4 hours; medium effort. Window behavior is tested with a simulated clock.

## 2. Dependencies and entry conditions

M13 complete and installed. Close-outs now admit all newly eligible work up to the existing cap,
and dispatch selects effort from Size through `claude_bg`. The status feed, usage holds and
flagless continuation machinery already exist. This milestone adds self-pacing; it does not
require M15 or make a new dependency on it.

## 4. Requirements, scope, non-goals

- **Covers:** SCOPE §6 M14 and §8 item 4; extends existing usage hold/admission behavior.
- **Scope:** additive `projects/<key>/budget.json` with `window_start`, `sessions_used`, `tier`;
  tier-aware pacing across the five-hour window; pre-exhaustion pause, recorded resume time,
  visible status and automatic window rollover without a failed dispatch.
- **Non-goals:** buying credits, metered API fallback, multiple accounts, a quota dashboard,
  replacing existing error waits or the cap, or deliberately exhausting the live subscription.

## 6. Interfaces

- **Introduces:** budget record with `window_start`, `sessions_used`, `tier`; deterministic
  admission result carrying a pause reason and resume time; window rollover and status rendering.
- **Consumes:** M13's admission/effort seam, existing cap and holds, per-session status feed,
  tick clock and log writer. All sessions share the one subscription; per-project state does
  not grant each project a fresh account allowance.

## 7. Implementation checklist (ordered)

1. Inspect available usage/reset evidence and tier configuration on the installed CLI. Distinguish
   observed allowance from the `sessions_used` pacing estimate; do not invent a guaranteed number
   of sessions for a subscription tier or query a metered API for it.
2. Add clock-controlled fixtures and the three-field budget record. Settle the unit counted,
   failed dispatch accounting, resume accounting and window_start source; normal repeated ticks
   must not charge the same dispatch again.
3. Apply a conservative admission decision before dispatch would exhaust the allowance. Record
   the budget pause and resume time once; leave active work intact and do not spend a failure
   attempt, escalate, or send a dispatch that the pacing rule already knows it cannot admit.
4. Roll the window at its recorded boundary, reset the window's count and admit waiting work
   automatically subject to the existing cap and other holds. Apply pacing to every automatic
   session-start route, including planning and later judgement/replan sessions through the seam.
5. Show the pause reason and resume time in `baton status`; show the lift after rollover. Keep
   real usage-limit waits and the person's reserve effective alongside this policy.
6. Run §8, document the tier/estimation decisions and M16's observation procedure, review and
   close out. Live quota exhaustion is not a test requirement for this milestone.

## 10. Risks and decisions this milestone settles

- **Sessions are not a fixed quota unit.** Usage depends on work and other account activity;
  state the conservative policy and how available actual usage/reset evidence constrains it.
- **A pause is not failure.** It must not feed the failure ladder or look like a running lane.
- **One account, several consumers.** Planning, judgement and work sessions share allowance;
  reuse admission and count evidence so a new route cannot bypass pacing.

## Completion evidence

### 1. What changed

- **Pacing has two guards, and the account's own word is the first.** The status feed already
  carried `rate_limits.five_hour.used_percentage` and `resets_at` — `docs/ARCHITECTURE.md` §3
  listed both as fields the tick reads, and nothing read them. `budget_reading` now does, by the
  rule `reserve_reading` keeps for the seven-day window: the freshest status file by modification
  time that holds the number, whoever wrote it, and no reading at all once that file's own
  `resets_at` has passed. At or above `budgetCeiling` (90; 100 is off) the pause bites and
  `resets_at` **is** the resume time, observed rather than estimated. The second guard is
  `sessions_used`, Baton's own count of session starts in the window, against `budgetSessions` —
  **0 by default, which is off**.
- **The pause is a `hold`, cause `budget`, model `all`**, written once and lifted once beside the
  `fableReserve` hold, carrying `resumes_at`, `reason`, `window_start`, `sessions_used`, `tier` and
  the reading's provenance. Derivation 12 reads a `budget` hold as holding every model, so
  `hold_bites` is **unchanged** and both automatic routes that start a session are paced through
  the one seam: `dispatch_run`'s filter loop (work milestones and the planning lane alike) and the
  ladder's `redispatch`. `budget-redispatch-paced` shows one hold withholding both.
- **The window rolls by itself.** With a feed boundary it is the span ending there; without one it
  ends one span after the oldest start still inside it, so a start ageing past `budgetWindowHours`
  leaves the count, the window's start moves forward and the pause lifts on the next tick, through
  the cap and every other hold. `budget-rollover` and `budget-rollover-cap` advance `$SHIM/now`
  mid-`cmd` and show the pause, the lift and the admission that follows.
- **The count guard is exact inside a tick.** `budget_room` is counted down in step 8's own loop
  beside the cap, because every session the pass starts is one no feed entry reports yet — a guard
  read only between ticks would let a whole cap's worth through past the allowance, which is the
  one gap the count exists to close (D-181).
- **A pause is not a failure and does not look like a running lane.** No `dispatch_failed`, no
  attempt, nothing on the ladder, no escalation; `baton status` prints it under the holds with its
  reason and the time it expects to lift.
- **A pause that outlives the boundary it named is closed and reopened.** Both guards normally lift
  at their own boundary, but a session a person ran through it can put the next window over the
  line too, and then the standing hold names a time that has passed and `status` reads "resume due"
  under a pause that is not lifting — the same confusion inverted that M14 exists to remove.
  `budget-pause-outlives-window` covers it.
- **Each project's record**, `projects/<key>/budget.json` with the three fields SCOPE §5 names,
  written after the dispatch pass so it is the tick's own answer rather than the one from before
  its work. Derived from the log, the feed and the clock, and read back by nothing.
- **No tier maps to a number of sessions anywhere.** Checklist item 1's inspection: `claude
  --version` reads `2.1.278 (Claude Code)`, and `claude --help` lists `agents`, `attach`, `auth`,
  `auto-mode`, `doctor`, `gateway`, `import`, `install`, `logs`, `mcp`, `plugin`, `project`,
  `respawn`, `rm`, `setup-token`, `stop`, `ultrareview` and `update` — no usage or tier command
  among them — and the feed names a percentage, never a count. `budgetTier` records the person's
  word for the plan and nothing is derived from it (D-179).

### 6. Known limitations

- **`sessions_used` under-reads what the account actually spent, by construction.** It counts
  session starts — a `dispatch`, or a `dispatch_failed` at stage `launch` or `service`. A resume, a
  copy fork, the wake session, a hand-run `baton dispatch` and the person's own work all spend
  allowance and are none of them starts. That is not an oversight: the feed's reading covers every
  one of them, and counting them here would double the half the reading already holds. The guard
  the count is, is a sub-tick guard, and only that.
- **`budgetCeiling` 90 is on by default, and that changes live behaviour on install.** At or above
  90% of the five-hour window Baton stops starting new sessions; work in flight runs on, resumes
  are still delivered, and a person who wants the previous behaviour sets `budgetCeiling: 100`.
  This is the milestone's point rather than a side effect, but it is the one value worth knowing
  before the next install.
- **The reading can be stale by design.** The feed is written per turn by whatever session is
  running, so on a quiet Mac the newest file can be some minutes old; its `resets_at` bounds how
  stale it can be, because a reading of a window that has ended is discarded. Within one tick the
  count covers the gap; across a quiet stretch nothing is starting anyway.
- **A system clock that jumps backwards makes the count read low** for the rest of that window.
  `budget_starts` walks the log backwards and stops at the first start outside the window, which
  relies on the log's append order being its time order; the alternative is an `iso_epoch` per
  dispatch event ever logged, twice a tick, for ever. Stated rather than guarded against, and it
  heals at the next boundary.
- **The estimated resume time can be early where the count is the guard** and more starts stand
  above the allowance than one boundary releases. It is the first of several boundaries and each
  tick computes the next; nothing waits on the value, so it costs a line a person read and not a
  minute of work.
- **Three `lib/` files changed beyond the one introduced carry decisions**, which crosses the plan's
  split rule. Not split, and D-182 records why.

### The review, and what it changed

`/review-2` ran two agents on Fable — a debugger and a code-auditor — over the diff, plus a hand
pass. No critical issues. Seven warnings, two of them the same finding reached independently, and
six suggestions; every warning is fixed and two suggestions are declined with their reasons here.

- **A hand-run `baton dispatch` was charged while `lib/budget.sh`'s own comment, REQ-BUDGET-03,
  D-180 and `CONTEXT.md` all said it was not** (both agents). The **documents** were wrong, not the
  count: "not paced" and "not charged" are two claims and only the first held. `verb_dispatch`
  never asks `hold_bites`, so no pause withholds a person's own act; but the session it started is
  a session on the same subscription, and a count that ignored it would read low by exactly the
  work a person did most recently. All four now say charged-and-not-paced.
- **The ladder route had the sub-tick gap D-181 closes on step 8** (CA1). `redispatch` runs inside
  steps 3 to 6, before the dispatch pass, and writes `dispatch` events gated by a hold computed
  before them; several lanes on the rung at once would each pass it. It now asks `budget_room` too.
  This is the finding the review earned its place for: the reasoning was already written down and
  had been applied to one route only.
- **A non-numeric pacing number silently disabled the count guard while the pass failed** (DB1).
  `[ three -gt 0 ]` exits 2 and the `|| return 0` beside it turned that into "the guard is off",
  while `--argjson` separately failed the pass — loud failure and silent admission at once, which
  inverts this codebase's rule that a pass which cannot answer withholds. `budget_int` now refuses
  by name, and `budget_room` reads all three numbers before its early return so the refusal reaches
  the dispatcher through something the dispatcher itself calls. The same trail found `budget_state`
  calling `budget_span` unguarded, carrying the failure's message forward as a number.
- **`budget_room` was not decremented for a charged failed start inside one pass** (DB1).
  `dispatch_run` now re-reads it on the miss path, where the `dispatch_failed` has just been written.
- **The scenario assertions did not gate** (CA1). No `cmd` used `set -e` and `tests/run.sh` records
  only the last line's status, so every `[ … = 1 ]` that was not last printed nothing and changed
  nothing — and `budget-rollover` had frozen a log with three holds and two lifts under a line
  asserting one of each. `set -e` is now on all fifteen, the redundant trailing restores are gone so
  the last line is a real check, and two scenarios' run 2 promptly exited 1 on assertions that had
  been false all along. Both are rewritten to facts true in both runs — `budget-rollover` now
  asserts the lift and that `window_start` moved to the next start, which tests §8's "consistent
  window/count state" directly instead of counting events — and both narrations corrected.
- **Nothing covered the reading guard lifting** (CA1), which is the overnight path M14 exists for:
  `budget-rollover-cap` lifts on the count, and `budget-pause-outlives-window` re-holds. Added
  `budget-reading-lifts` (95% → a fresh file at 12% → lift and dispatch, no clock movement) and
  `budget-reading-expires` (95% past its own `resets_at` with no newer file → lift, the "night
  nothing else ran" case `budget_reading`'s comment argues for).
- Taken as suggested: a `resets_at` more than a span ahead is clamped to now, so a clock skew
  cannot silently zero the count; `window_start` is null where `source` is `empty`, so a quiet night
  stops rewriting every record every minute; `window_start_epoch` and `ends_epoch` are dropped as
  unread; `civil_from_days` names Hinnant and explains its four constants; REQ-BUDGET-02's
  acceptance column says the planning lane is paced by construction rather than implying a fixture.
- **Declined, with reasons.** Reopening the hold whenever `ends` moves — it would rewrite the hold
  each time the sliding window's oldest start ages out, which is the line-a-minute the once-only
  discipline exists to prevent; the current rule reopens only when the named time has passed, and
  the residual is a `reason` naming the percentage at the moment the pause fired, which is arguably
  the more useful of the two. Factoring `budget_reading` and `reserve_reading` into one
  window-taking function — deliberate, and the reviewer's own test is right: the third copy is when
  to do it, not the second.
