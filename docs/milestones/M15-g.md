# M15-g — A replan must replace something

## 1. Identity

- **ID:** M15-g. **Objective:** a replan is adopted only when the planning session changed the plan
  or a brief after the request, and a refused candidate does not stand on `main` as the accepted plan.
- **User-visible result:** a planning session that commits nothing cannot have the old plan adopted
  as its replacement; a candidate Baton refuses is undone before the next attempt and reaches a
  person only when the attempts run out.
- **Size:** Medium, about 3 hours; high effort. Natural split point: after §4 item 1.

## 4. Requirements, scope, non-goals

**The finding.** A review on 2026-10-01 (findings R02a and R02b), confirmed by reading the code:

- **R02a.** `planning_landed` takes "a proved completion after the request" as the record that the
  plan or a brief changed. But every replan reuses the planning branch `m00-plan`, and
  `completion_baseline` returns the *first* baseline recorded on a branch, the first generation's.
  A replan session that commits nothing and names `main`'s head as `merged_as` is still proved
  against that old baseline, the unchanged plan validates, and Baton adopts the plan it was asked to
  replace, closes the park and redispatches the unchanged brief.
- **R02b.** The planning session merges its candidate to `main` before Baton measures it. A refused
  candidate stays there; one that does not parse raises `self_check`'s `plan-unparseable` project
  park, with a Mac message, while attempts remain.

**Scope.**

1. **Bound to the request.** For the planning lane, the completion a replan waits for is measured
   from the commit `main` stood at when the request was written (or the dispatch for that request,
   whichever the request event records), never from an earlier generation's baseline; and it must
   show a changed path in the plan document or a brief. Settle where that binding lives, in
   `completion_baseline` for the planning lane or in `planning_landed`, against M20's change.
2. **A refused candidate is undone.** The next planning attempt's prompt names the accepted plan's
   commit and the refused candidate's, and the session restores the accepted documents before it
   writes a new candidate; while a replan request has attempts left, a `plan-unparseable` caused by
   the planning lane's own merge is held as the replan's, not raised as a project park with a
   message. Exhaustion reaches the person once, as M15-e defines. Baton itself never commits to the
   project: restoring is the planning session's work.

**Non-goals.** No change to M12's first generation, to the validator's rules, or to how a person
repairs a plan by hand. No new event kind beyond what the request already carries.
