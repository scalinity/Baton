Depends on M03. This brief follows contract 2 and the hardened foundation.

## Scope

Introduce durable delivery operation IDs and correlate acknowledgements to exact provider typed-record UUIDs. Record delivery intent before stop/resume. Ambiguous deliveries remain pending; never infer successful delivery from an exit code alone. Preserve a recovery episode across new runs. One resume and one redispatch are the episode budget before escalation; only verified progress or explicit reset restores it. Verify saved options/copy-fork behavior through the adapter for the supported version. Retire stale session writers before acknowledging replacement sessions.

## Acceptance

Full resume → redispatch → failure escalates across attempts; missing observation is not a crash; lost delivery acknowledgement is reconciled without duplicate prompt; old-session/old-delivery endings cannot mutate the current run; interrupted tool work is inspected before replay; context/usage errors do not erase identity.

Run sh tests/run.sh and add behavior assertions for the new transitions. Use fault injection at
new effect boundaries, not only snapshot comparisons. Use two independent reviews and address
concrete findings. No build, live session, launchd or target-project operation is implicit in the
fixture test suite. Obtain any required explicit authorization before a live acceptance action.


## Cross-layer acceptance

- F-39/F-40: replay a delivery acknowledgement and submit an older ending after a newer delivery.
  Only the correlated current operation may advance; filename or timestamp order cannot decide it.
- F-41: distinguish a verified transient response, a quota wait, a configuration/authentication
  failure, an incompatible observation and an unclassified error. Unknown evidence holds for
  diagnosis; it is not automatically context exhaustion or a reason to change model.
- F-25/F-41: exercise the full recovery episode across new run IDs/attempts. Record retry bounds
  and elapsed-wait policy separately; unverified progress and process creation do not reset them.
- Preserve the exact selected model and authorized scope through retry or record an explicitly
  authorized change. Do not silently choose a fallback to make the fixture succeed.
- Test completed-but-still-live and obsolete provider sessions. Any retirement needed by policy
  is an identified, ownership-guarded stop with an observed outcome; consumption alone neither
  terminates the session nor proves that execution capacity was released.

## Recovery procedure

Inspect existing code, durable action records, candidate work and prior evidence. Resume only the
unfinished part. Do not reset failure budgets, duplicate external effects, overwrite human work,
or weaken an invariant to make a continuation succeed. Split scope into a real plan row if needed.
