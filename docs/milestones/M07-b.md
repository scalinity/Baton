# M07-b — A finished session: offline when idle, awake when messaged

## 1. Identity

- **ID:** M07-b, split from M07 by the ruling on its question (D-081). **Objective:** a finished
  session costs nothing while nobody is using it and needs no terminal when somebody is. Its
  process goes offline once it has sat idle on a closed lane; a message the person sends to it in
  Claude.app or on the phone brings it back and is answered; when the person is done it goes offline
  again. Settle whether Claude.app can group Baton's sessions under their project instead of
  "Other", and build it if Claude Code offers a way. Make the takeover rule see a person typing
  through Remote Control.
- **User-visible result:** the person opens any finished milestone's session in Claude.app, types,
  and the session answers — no command, no terminal; an idle one is not holding a process; the
  takeover rule stands Baton off a lane the person has typed into from the app.

session is on Remote Control (D-081). Milestone worktrees are kept and the Stop gate and StopFailure
hook stand down on an archived `complete` handover (D-078), so a woken finished session is not asked
for a handover.

## 7. Implementation checklist (ordered)

1. **Measure, before building anything, which mechanism wakes a stopped session on a message** —
   live, fixture project only, with the person sending the messages from Claude.app. In this order,
   stopping at the first that works:

     internal setting `autoAddRemoteControlDaemonWorker` beside `remoteControlAtStartup`. With it
     `true` in `~/.claude/settings.json` (a person's edit, asked for with an `asking` artifact and

     Claude.app, and read `~/.claude/daemon.log` and the transcript: does the service spawn or resume
     the session and deliver the message?
   - (b) **A Remote Control server environment per project.** `claude remote-control` in server mode
     polls claude.ai for work and spawns a session process when a message arrives, then returns the
     session to idle when it finishes (the 2.1.270 binary's `[bridge:work] Starting poll loop
     spawnMode=… maxSessions=…`, `[bridge:session] Spawning sessionId=…`, `[bridge:session] Session …,

## 10. Risks and decisions this milestone settles

- **A person may be reading a session the rule would take offline.** Reading changes no transcript;
  the wake is the undo. Settle `idleStopMinutes` with that in mind.
- **Every stop Baton makes archives the session on claude.ai.** The consume of an `asking` artifact
  stops the session so the ruling resumes it rather than a copy (REQ-ESC-06); M07's own park had to
  be unarchived in Claude.app before a message could be typed to it. The server mode unarchives a
  reaped session before reattaching; settle what the chosen wake does, and whether a flagless resume
  unarchives. The stop itself stays: without it the ruling forks a copy (M05's live proof).
- **Memory is the cost being managed:** about 450 MB per idle session, connected or not (M07).
- **The takeover rule does not see a person typing through Remote Control.** It reads `user` records
  with `promptSource: "typed"` (derivation 3, INV-04). In M07's own transcript every message the
  person sent from Claude.app arrived as a `queued_command` attachment with `origin: {kind:
  "human"}` — mid-turn, removed as `absorbed_mid_turn` — and the message delivered on a wake in
  Probe07 M01 arrived the same way; the only three `typed` records were Baton's own prompts. With
  every session on Remote Control this is how a person types into one, so Baton can prompt over a
  person today. Settle what a message sent between turns looks like, and count a person's
  `queued_command` as a takeover.

### The question this raises

A process that is stopped cannot answer a message, and a process that runs costs 0.35–0.8 GB. The
three designs, each with its cost:

1. **Keep every finished session running.** No offline rule. A message to any finished session is
   answered at once, in its own thread. Memory grows by one session per milestone with no bound —
   about 8–16 GB across the twenty ahead — and an update of the CLI restarts them all.
2. **Keep the three most recently finished running; take older ones offline once idle
   `idleStopMinutes`; reach an older one by messaging one always-on session, `Baton · wake`, from the
   app or the phone** ("M05: what did you decide about X?"), which runs `baton wake M05 "<text>"`: a
   flagless resume carrying the text, answered in M05's own thread, which the resume makes active
   again. Bounded at four processes (about 2–3 GB). One model turn per wake in the wake session; that
   session is itself a long-lived session whose context grows.
3. **Keep the three most recent running; older ones offline; reach an older one only from the Mac**
   — `baton wake M05` in a terminal, or M07-c's notification click. Bounded at three processes; the
   phone cannot reach an offline session at all.

Recommended: 2. The sessions a person goes back to are mostly the recent ones, which answer in their
own thread with nothing else; an older one is one message away from the phone; and the memory stays
bounded on a plan that will finish twenty more milestones. `baton wake` is the verb all three
reaching paths share, so it is also the fallback the brief allows.
