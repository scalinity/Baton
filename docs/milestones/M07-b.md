# M07-b — Session lifecycle and project grouping

## 1. Identity

- **ID:** M07-b, split from M07 by the ruling on its question (D-081). **Objective:** a finished
  session stays reachable without holding a process for ever. Its process goes offline once it has
  sat idle on a closed lane, and comes back on demand with anything the person typed to it while it
  was away. Settle whether Claude.app can group Baton's sessions under their project instead of
  "Other", and build it if Claude Code offers a way.
- **User-visible result:** a closed lane's session that has been idle for `idleStopMinutes` is
  stopped by the tick and says so in `launchd.out` and the log; `baton wake <milestone>` (or
  `<project>/<milestone>`) restores its worktree if it is missing and resumes it, and a message typed
  to it in Claude.app while it was offline arrives; the grouping question is answered in this brief
  with its evidence, and built if a mechanism exists.

## 2. Dependencies and entry conditions

M07 complete and installed — M07's close-out runs `sh install.sh` itself (D-079). Every dispatched
session is on Remote Control (D-081). Milestone worktrees are kept and the Stop gate and StopFailure
hook stand down on an archived `complete` handover (D-078), so a woken finished session is not asked
for a handover.

## 7. Implementation checklist (ordered)

1. Measure before building (live, fixture project only): how long an idle finished `--bg` session's
   process lives without intervention, and whether any stop other than `claude stop` takes the
   process offline without claude.ai archiving the session. M07 measured that `claude stop` archives
   it and that the M04–M06 sessions ended by a service restart were not archived.
2. The offline rule, run per project after step 4: a session whose lane is closed — its milestone's
   newest archived handover for that session is `complete` — whose row has a pid, reads idle (not
   busy, not waiting), and whose transcripts have not changed for `idleStopMinutes` is stopped, once,
   with one event. Never an open lane (that is the ladder's), and never a row whose `waitingFor` is
   set.
3. `baton wake`: resolve the milestone across projects as `baton answer` does; find its newest
   session in the log, through copy forks; recreate `../<Project>-<milestone>` from its branch with
   `worktree_ensure` if the directory is gone; refuse if a live row already carries the session;
   resume flagless with a fixed wake line that asks for nothing; write the sidecar and a `resume`
   event only if the lane is open, and otherwise record the wake as the offline event's counterpart.
4. The grouping investigation: what Claude.app's sidebar groups a Remote Control session by. M07
   found the registration sends `environmentId`, `title`, `gitRepoUrl`, `branch`, `defaultBranch`,
   `permissionMode` and `tags`, and that an `origin` fetch URL alone still lists under "Other". Try
   the remaining fields that a `--bg` session can set; build it only if one works.
5. The fixtures, twice each: the offline rule acting, and refusing for an open lane, a waiting row, a
   busy row, a recent transcript and an unreadable row; `wake` restoring a missing worktree, refusing
   a live session, and resolving ambiguity.
6. `sh tests/run.sh`, `/review-2`, `/address`, completion evidence, the handover.

## 10. Risks and decisions this milestone settles

- **A person may be reading a session the rule would stop.** Idle-and-quiet is the whole test;
  reading does not change a transcript. The wake is the undo, and it is one command. Settle the
  threshold with that in mind.
- **Archiving on claude.ai.** If only `claude stop` takes a process offline, every offline session
  must be unarchived in Claude.app before typing; say so in the verb's output.
- **Every stop Baton already makes archives a session too.** The consume of an `asking` artifact
  stops the session so the ruling resumes it rather than a copy (REQ-ESC-06), and M07's own park
  showed the result: the session was archived in Claude.app and had to be unarchived before a message
  could be typed to it. Settle whether a flagless resume unarchives it (the docs say
  `claude remote-control --session-id` does from v2.1.228; a `--bg --resume` was not observed) and
  record it; the stop itself stays, because without it the ruling forks a copy (M05's live proof).
- **Memory is the cost being managed:** about 450 MB per idle session, connected or not (M07).
- **The takeover rule does not see a person typing through Remote Control.** It reads `user` records
  with `promptSource: "typed"` (derivation 3, INV-04). In M07's own transcript every message the
  person sent from Claude.app arrived as a `queued_command` attachment with `origin: {kind:
  "human"}` — mid-turn, and removed as `absorbed_mid_turn` — and the one message delivered on a wake
  in Probe07 M01 arrived the same way; the only three `typed` records were Baton's own prompts. With
  every session on Remote Control (D-081) this is the common way a person types into one. Settle
  what a message sent from the app between turns looks like, and make derivation 3 count a
  person's `queued_command` as a takeover, with a fixture shown failing first.
