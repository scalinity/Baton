# M11 — `baton onboard <path>`

## 1. Identity

- **ID:** M11. **Objective:** register an unfamiliar Git repository and adapt its existing plan
  without making a person first reshape the repository for Baton.
- **User-visible result:** `baton onboard <path>` states the project's intent and what done
  looks like in about three lines, takes one yes/no confirmation, and makes its plan usable.
- **Size:** Large, about 5–7 hours; high effort. Registration, adaptation and the permission
  boundary are the substantial work; use the split rule if they exceed one session.

## 2. Dependencies and entry conditions

M09 and M10 complete and installed. Their delivered behavior is new worktrees under
`$BATON_HOME/worktrees/<project>/<milestone>`, preservation of existing recorded session paths
unless supported same-session relocation was proved, verified desktop grouping, and completion proof
with `baseline`, `changed_paths` and Baton-produced `check_result`. Read the current interfaces
in the repository; do not assume sibling-session memory. Use disposable Git repositories for
proof; no manual plan migration, registration file or seed artifact is an entry condition.
Read M09's recorded limitations: grandfathered legacy paths do not mean relocation succeeded.

## 4. Requirements, scope, non-goals

- **Covers:** SCOPE §6 M11, §9's partway-through-plan requirement, and §8 item 1's onboarding;
  extends REQ-PLAN, REQ-PERM and REQ-VERB.
- **Scope:** arbitrary owned Git repository path; registration and toolchain-derived permission
  list; tolerant existing-plan adaptation; conforming briefs/close-out instructions and starting
  handover where absent; exactly one routine intent confirmation. Persist `goal`, `plan_format`
  (`native`, `adapted`, `generated`) and `onboarded_at` in `projects/<key>/project.json`.
  The same confirmation writes a **confirmed intent record** carrying the goal *and* explicit
  constraints and non-goals (F10); migrates an existing registration into that representation
  without resetting progress (F11); settles the planning/judgment session lifecycle — request
  identity, terminal outcomes, restart behaviour, admission-slot ownership — before the first
  judgment session runs (F03); and adds CLI-shape checks for what the new session roles actually
  consume (M4).
- **Non-goals:** inventing a plan where none is usable (M12), a plan approval gate, hand-migrating
  Reclaim (superseded M08), direct API calls, non-Git paths, or rewriting application code. The
  intent record is not a second approval gate: it widens what one confirmation records, and adds no
  human touchpoint.

## 7. Implementation checklist (ordered)

1. Inspect the registration recipe and deny rules. Trace an onboarding request from the verb
   through the tick; protected registration writes must occur outside a dispatched session's
   denied context, not through a widened deny list or a session writing state directly.
2. Add fixtures: native plan, plan missing Model, other omitted optional columns, reordered
   columns, missing brief instructions, and a partially completed plan. Preserve valid IDs,
   dependencies, completed milestones and real holds; defaults must not turn prose into tokens.
   Include retired/superseded source statuses: the native Status vocabulary is only `done`,
   `held` or blank. Map retirement to `held` with the reason in a prose column, never to done
   or runnable, and do not invent a gate for something that will never be cleared.
3. Detect the canonical Git project, toolchain and standing check; derive the allowlist from
   those facts while retaining the two deny classes. Derive the intent statement from repository
   evidence; route any necessary judgement through the subscription-authenticated Claude CLI.
4. Present about three lines stating the project and done, then yes/no. Persist the confirmed
   goal and provenance only after yes. A no leaves work undispatched; correction is about intent,
   not a second routine plan approval. Do not silently confirm a guessed goal.
5. Adapt an existing usable plan and its missing contract material automatically. Keep one
   authoritative graph; preserve already completed milestones so joining mid-plan cannot restart
   them. Establish the initial handover with explicit runnable milestone names and brief pointers.
6. For no usable plan, record the confirmed goal and an actionable handoff for M12's generation
   path; do not implement that generator here or present a missing plan as successful adaptation.
7. Verify repeat onboarding does not duplicate registration, reset progress or seed work twice.
   Run §8, document interfaces and any V1 wording superseded by this scope, review and close out.

**Natural split point after item 4.** Confirmed registration and permission derivation stand
alone; tolerant adaptation and initial handover are the bounded remainder. Follow the plan's
split rule, record unfinished acceptance and do not mark M11 complete at the split.

## 10. Risks and decisions this milestone settles

- **Permissions cannot bootstrap themselves.** L1/M08 exposed denied registration writes;
  the tick must perform them. Unknown permissions requiring an access grant remain human facts.
- **Tolerance can erase intent.** Default absent columns without discarding progress or real
  gates; distinguish unusable plan input from a usable plan needing adaptation. Rich source
  status vocabularies need semantic mapping: M08 demonstrates retirement borrowing `held`.
- **V1's Reclaim rule is obsolete.** SCOPE §9 supersedes M08 and its migration gate. Update
  relevant standing documentation as this automatic path lands; do not recreate the manual path.
- **A goal is not a constraint.** "Run an unfamiliar project unattended" does not contradict
  "replace the controller with Swift and SQLite", so a goal-only guard would have passed V2 — the
  one thing it exists to catch. The confirmed intent record must make that pair decidable, and the
  milestone owes the regression: one goal, two proposals, one permitted and one forbidden. For
  Baton the record names the controller's POSIX-shell boundary and excludes a Swift/SQLite
  replacement. The guard receives the record and the work, never the author's rationale.
- **Reinstalling cannot repair a registration.** `install.sh:131-133` writes `{path, plan}` only
  when `projects/<key>/project.json` is absent, so a registration that predates the intent record
  can never gain one by reinstalling. Migration is this milestone's, and it must not reset progress.
- **A special session can deadlock the cap.** A guard or planning session that holds an admission
  slot while its own result is awaited is a lane nothing will close. D-130 bears on this:
  `do_unresolved` counts a launch that could not be proved to have started nothing, so a role with
  no terminal outcome holds that count open. Settle the roles before the first judgment session,
  not after one wedges.

## Completion evidence

### 1. What changed

- **`baton onboard <path>` is the eighth verb, and the relay writes Baton's state.** L1's recorded
  defect was that registration presupposed a migrated plan, conforming briefs, close-out
  instructions, a permissions file and a starting artifact, and that `install.sh` generated the
  first two only for the project it runs in — while M08 asked a *dispatched session* to write
  `projects/<key>/project.json`, a path its own deny rules forbid. The verb takes the lock, writes
  the registration and the rail itself, and appends one `onboarded` event. Nothing is widened and no
  session writes those paths.
- **The target repository is not written.** No commit, no file, no working-tree change — measured
  before and after in `onboard-native`, `onboard-adapted-columns`, `onboard-missing-brief-contract`
  and in the live proof. What a plan needs in order to be read is recorded as the registration's
  `adaptation` and applied by `plan_tables`. A `Model` column Baton chose would be Baton's state
  inside someone else's document (REQ-CONTRACT-02), and an adaptation that lives only in the
  registration is undone by deleting it (D-156).
- **Tolerance is registered per project, not global.** A project registered `native` is read exactly
  as strictly as before — `plan-bad-status` still parks on `"in flight"`. A project registered
  `adapted` is read with that registration's `defaults` (the named columns may be absent, and supply
  their value where the column is absent *or* its cell is empty — the two shapes of L1's symptom),
  its `status_map`, and `gates: "absent"` for a plan with no gates table. A `Status` word neither
  native nor mapped still fails the read, with the words named (D-157).
- **Retirement borrows `held`, with its reason as prose.** Never `done`, which would let a successor
  inherit it as a satisfied dependency; never blank, which would make it runnable; and no gate,
  because a gate is a hold a person clears and retirement waits for nobody. `onboard-status-vocabulary`
  shows M03 `retired` reading `held` and M04 waiting on it for ever.
- **The milestone table is located by having an `ID` header cell in any position**, which is what
  REQ-PLAN-01 already said. The reader required `ID` to be the *first* cell, so a project whose own
  table opens with `Owner` was reported as having no plan — found by the reordered-columns import
  case (REQ-PLAN-10).
- **The starting handover closes L1's other half.** `intersect_verdicts` reads a project no handover
  has ever named as silence: with no handover in force an eligible milestone yields no candidate
  *and* no `omitted` park (`lib/candidates.sh:118-127`). Onboarding records every milestone the plan
  makes eligible, with a disposition and a brief pointer, in the registration's `start`, and
  `dispositions_in_force` reads it after every archived handover, so the first real one supersedes it
  entry by entry (D-158). It is not a completion claim: it names no merge and is checked as none.
- **The standing check comes from the same evidence as the rail.** A project registered without a
  `.check.command` has a completion Baton cannot prove (D-147), so it is derived beside the allow
  list from the detected toolchain, a project-specific runner winning over a language's canonical
  command. The two deny classes are unchanged and now live once, in `onboard_deny_rules`, which
  `install.sh` sources — its composed `permissions.json` is byte-identical to what it wrote inline
  (D-160).
- **The two session roles are written down before either runs (F03).** A **judgment request** is a
  foreground `claude -p` inside a verb, bounded by a deadline, with no name, row, attempt or
  artifact: it takes no admission slot, so the cap cannot be deadlocked by a role awaiting its own
  result. A **judgment session** takes a slot, owes an artifact, and is never awaited inside a verb
  or a tick. `docs/ARCHITECTURE.md` §4.5 (D-159).
- **The confirmation records constraints and non-goals, not the goal alone (F10).** One confirmation,
  three lines, a wider record. `onboard-intent-regression` measures the claim SCOPE §8 item 6 makes:
  for one goal and two proposals, the goal alone bears on neither, and the record forbids only the
  controller replacement.
- **An existing registration migrates additively (F11).** `install.sh:131-133` wrote `{path, plan}`
  only when the file was absent, so reinstalling could never supply a field registration lacked.
  Onboarding supplies it, keeps a `check.command` a person set by hand, keeps every other field, and
  resets no progress.
- **Contract material Baton cannot author is named with its repair, not invented.** The onboarding
  report ends with `plan_preconditions_report`, so a brief with no fenced kickoff prompt and a brief
  that does not exist are both named per milestone at the moment of onboarding rather than one
  refused dispatch at a time. Baton can read a plan it did not author; writing a milestone's brief is
  generating a plan, which is M12's.

### 6. Known limitations

- **A project onboarded with no usable plan parks as `plan-unreadable` on the next tick** (D-162).
  The park is true — a project whose plan file does not exist cannot be driven — and it is raised
  once, but it sits in `baton status` until M12 writes the plan `plan_owed` says is owed.
- **The brief pointer is the contract's path, so a project that files its briefs elsewhere has every
  one reported missing.** `docs/milestones/<ID>.md` is what `dispatch_one` constructs whatever a
  pointer says — `01-findings.md` finding 3 records that the pointer and the dispatch are not
  unified, and unifying them is not this milestone's — so a derived pointer would be one Baton will
  not read. `onboard-plan-elsewhere` registers a plan at `docs/plan/roadmap.md` and still points its
  briefs at `docs/milestones/`, which is the truth about where Baton will look.
- **The toolchain detection is a fixed list of seven kinds.** A repository whose build is none of
  them is registered with no `check.command`, which makes its completions `unrun` (D-147) and parks
  the project rather than proving anything. The list is where a new kind goes; nothing infers one.
- **The status vocabulary is a fixed list too**, and deliberately: a word it does not know refuses the
  onboarding with the word named rather than being guessed at. Widening it is an edit to
  `onboard_status_propose`, made once, for a word a person has seen.
- **The plan search is bounded at three directories and prunes four names.** A plan deeper than that,
  or under a directory the prune names, is not found; naming it in the registration's `plan` is the
  repair, and the registered pointer is always tried first.
- **The judgment request's deadline counts sleeps, not wall clock**, as `completion_check_run`'s does:
  it is a lower bound, and a Mac that sleeps spends it while asleep.
- **Nothing pins the CLI's `-p` output shape beyond the four labels.** `onboard_cli_shape` records the
  version and refuses a binary that will not answer `--version`; a `-p` whose output stopped carrying
  the labels refuses the onboarding with "answered without a GOAL: or DONE: line", which is a refusal
  and not a silent wrong answer, but it is not a version pin (M4's stated scope).
- **`onboard_cells` and `plan_extract` are two implementations of one cell-splitting rule.** Composing
  awk programs in POSIX shell means building them as strings, and the reader's is already large; what
  keeps them in step is that onboarding asks the first for every question it has about a plan's shape,
  so there are two and not four, and each of the new scenarios reads a plan one way and parses it the
  other.
