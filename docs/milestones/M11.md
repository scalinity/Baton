# M11 — `baton onboard <path>`

## 1. Identity

- **ID:** M11. **Objective:** register an unfamiliar Git repository and adapt its existing plan
  without making a person first reshape the repository for Baton.
- **User-visible result:** `baton onboard <path>` states the project's intent and what done
  looks like in about three lines, takes one yes/no confirmation, and makes its plan usable.
- **Size:** Large, about 5–7 hours; high effort. Registration, adaptation and the permission
  boundary are the substantial work; use the split rule if they exceed one session.

## 2. Dependencies and entry conditions

M09 and M10 complete and installed. Their delivered behavior is new worktrees under
`$BATON_HOME/worktrees/<project>/<milestone>`, preservation of existing recorded session paths
unless supported same-session relocation was proved, verified desktop grouping, and completion proof
with `baseline`, `changed_paths` and Baton-produced `check_result`. Read the current interfaces
in the repository; do not assume sibling-session memory. Use disposable Git repositories for
proof; no manual plan migration, registration file or seed artifact is an entry condition.
Read M09's recorded limitations: grandfathered legacy paths do not mean relocation succeeded.

## 3. Required reading

`CLAUDE.md`; `CONTEXT.md`; `CONTRACT.md`; `docs/v1.1/SCOPE.md` in full, especially §5, §6 M11
and §9; `docs/MILESTONES.md`; `docs/v2/01-findings.md` limitation 1 and MILESTONE FORMAT;
`docs/SPEC.md` §2.1, §2.6, §2.8, §2.10, §7.1; `docs/ARCHITECTURE.md` §3, §4.1–4.3, §7, §10;
`docs/DECISIONS.md` D-021, D-089, D-091; `install.sh` registration and permissions generation;
`bin/baton`, `lib/plan.sh`, `lib/answer.sh` permission-writing path, `lib/tick.sh`;
M09 and M10 completion evidence.

## 4. Requirements, scope, non-goals

- **Covers:** SCOPE §6 M11, §9's partway-through-plan requirement, and §8 item 1's onboarding;
  extends REQ-PLAN, REQ-PERM and REQ-VERB.
- **Scope:** arbitrary owned Git repository path; registration and toolchain-derived permission
  list; tolerant existing-plan adaptation; conforming briefs/close-out instructions and starting
  handover where absent; exactly one routine intent confirmation. Persist `goal`, `plan_format`
  (`native`, `adapted`, `generated`) and `onboarded_at` in `projects/<key>/project.json`.
- **Non-goals:** inventing a plan where none is usable (M12), a plan approval gate, hand-migrating
  Reclaim (superseded M08), direct API calls, non-Git paths, or rewriting application code.

## 5. Expected files (proposed)

`bin/baton`; new `lib/onboard.sh`; `lib/plan.sh`; narrow integration in `lib/tick.sh` and
`install.sh`; `tests/scenarios/onboard-*`; `docs/SPEC.md`; `docs/ARCHITECTURE.md` §10 row M11;
`docs/DECISIONS.md`; this brief and successor prompt refreshes. Assess the split rule before
editing more than two existing library files. Outside the repository: registration/permissions
under `$BATON_HOME/projects/<key>/`, starting handover and fixture target plan/brief instructions.

## 6. Interfaces

- **Introduces:** `baton onboard <path>`; confirmed `goal`, `plan_format`, `onboarded_at`;
  tolerant import into the existing plan contract and a no-usable-plan result for M12.
- **Consumes:** install's registration recipe, detected toolchain and target standing check,
  the current plan reader, permission composition, managed worktrees, completion verification,
  and the tick-owned mailbox/log path. Keep the tick as writer of protected registration state.

## 7. Implementation checklist (ordered)

1. Inspect the registration recipe and deny rules. Trace an onboarding request from the verb
   through the tick; protected registration writes must occur outside a dispatched session's
   denied context, not through a widened deny list or a session writing state directly.
2. Add fixtures: native plan, plan missing Model, other omitted optional columns, reordered
   columns, missing brief instructions, and a partially completed plan. Preserve valid IDs,
   dependencies, completed milestones and real holds; defaults must not turn prose into tokens.
   Include retired/superseded source statuses: the native Status vocabulary is only `done`,
   `held` or blank. Map retirement to `held` with the reason in a prose column, never to done
   or runnable, and do not invent a gate for something that will never be cleared.
3. Detect the canonical Git project, toolchain and standing check; derive the allowlist from
   those facts while retaining the two deny classes. Derive the intent statement from repository
   evidence; route any necessary judgement through the subscription-authenticated Claude CLI.
4. Present about three lines stating the project and done, then yes/no. Persist the confirmed
   goal and provenance only after yes. A no leaves work undispatched; correction is about intent,
   not a second routine plan approval. Do not silently confirm a guessed goal.
5. Adapt an existing usable plan and its missing contract material automatically. Keep one
   authoritative graph; preserve already completed milestones so joining mid-plan cannot restart
   them. Establish the initial handover with explicit runnable milestone names and brief pointers.
6. For no usable plan, record the confirmed goal and an actionable handoff for M12's generation
   path; do not implement that generator here or present a missing plan as successful adaptation.
7. Verify repeat onboarding does not duplicate registration, reset progress or seed work twice.
   Run §8, document interfaces and any V1 wording superseded by this scope, review and close out.

**Natural split point after item 4.** Confirmed registration and permission derivation stand
alone; tolerant adaptation and initial handover are the bounded remainder. Follow the plan's
split rule, record unfinished acceptance and do not mark M11 complete at the split.

## 8. Fixtures, verification, acceptance

- **Fixture-run:** every import case in item 2; yes/no intent outcomes; denied-session versus
  tick-owned registration; toolchain permissions; no-plan handoff; repeated onboarding;
  mid-plan progress preservation, retirement/status mapping and no duplicate seed;
  each twice, then `sh tests/run.sh`.
- **Manual, live:** onboard a disposable unprepared Git repository with an existing non-native
  plan through the public verb, with one intent confirmation and no preparatory repository edit.
- **Acceptance:** the unprepared repository is registered and its existing plan parses without
  a human editing it first; missing Model is tolerated; confirmed goal/provenance are stored;
  a repository already partway through its plan joins without replaying completed milestones;
  retired source work stays non-runnable and does not count as a completed dependency.

## 9. Definition of done and evidence

Ten-item handoff with before/after target documents, the three-line confirmation and response,
registration field values, derived permissions, `baton plan` output and the starting handover.
Record who wrote protected files and show that no manual migration commit was needed.

## 10. Risks and decisions this milestone settles

- **Permissions cannot bootstrap themselves.** L1/M08 exposed denied registration writes;
  the tick must perform them. Unknown permissions requiring an access grant remain human facts.
- **Tolerance can erase intent.** Default absent columns without discarding progress or real
  gates; distinguish unusable plan input from a usable plan needing adaptation. Rich source
  status vocabularies need semantic mapping: M08 demonstrates retirement borrowing `held`.
- **V1's Reclaim rule is obsolete.** SCOPE §9 supersedes M08 and its migration gate. Update
  relevant standing documentation as this automatic path lands; do not recreate the manual path.

## 11. Handoff and next milestone

`Copy-ready session prompt`.

At close-out, after recording this milestone as done, re-read the plan's current Status cells,
dependencies and gates. List every direct successor in `eligible[]`, even if it cannot run yet,
and also every other milestone the plan then makes eligible. Derive each disposition at that
moment, with an open gate taking precedence:

- `held` — an open gate holds it; set `held_by` to that gate's exact name.
- `wait` — no open gate holds it and at least one dependency is not done; set `wait_for` to
  the IDs of all dependencies not yet done.
- `run` — every dependency reads done and no open gate holds it.

Use `docs/milestones/<ID>.md` and heading `Copy-ready session prompt` for each entry. Refresh
every listed prompt on main, carrying the actual onboarding verb, stored-goal and no-plan

never change dependencies or add a gate to obtain it. Baton initiates successors; this session
does not. There is no new person review of the generated plan.
