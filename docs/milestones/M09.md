# M09 — Where sessions live, and how they surface

## 1. Identity

- **ID:** M09. **Objective:** keep Baton's worktrees under its own home, preserve existing work,
  and put dispatched sessions under their project in the desktop sidebar.
- **User-visible result:** no sibling worktree debris in Finder; completed, merged worktrees
  expire after a grace period; sessions appear under their project rather than Other.
- **Size:** Small, about 2–3 hours; medium effort. Host investigation is the uncertain part.

## 2. Dependencies and entry conditions

M17-b complete and installed; M10 can run independently. The existing V1 relay is installed. Inspect the
host's `claude --help`, worktree inventory and session rows before choosing a grouping mechanism
or relocating a working directory. This milestone does not depend on M10's new completion fields.

**Kickoff:** M09 is not a root. It depends on M17-b, and M17-b's close-out lists it with disposition
`run`, so the tick admits it — nothing about M09 is hand-dispatched, as SCOPE §7 specifies. M10 is
M09's sibling under the same parent, admitted by the same handover; this M09 session does not start
or restart M10 and does not assume which sibling will finish first.

`CLAUDE.md`; `CONTEXT.md`; `CONTRACT.md`; `docs/v1.1/SCOPE.md` in full, especially §6 M09;
`docs/MILESTONES.md`; `docs/SPEC.md` §2.7, §2.12, §5; `docs/ARCHITECTURE.md` §3, §4.1, §6.2,

## 4. Requirements, scope, non-goals

- **Covers:** SCOPE §6 M09 and §8 item 2; REQ-DISPATCH's worktree rules and REQ-LIFE where
  indefinite worktree retention conflicts with the new policy.
- **Scope:** `$BATON_HOME/worktrees/<project>/<milestone>`; migration with branches intact;
  prune only when done, verified merged and older than the retention window (default seven days);
  dirty worktrees always retained; branches always retained; actual desktop grouping.
- **Non-goals:** changing transcript retention, deleting branches, a new session manager,
  completion-proof strengthening (M10), non-Git projects, or a language rewrite.

## 5. Expected files (proposed)

`lib/dispatch.sh`; a small worktree module if the responsibility needs its own file;
`lib/tick.sh`; `tests/scenarios/worktree-*`; existing prune fixtures; `CONTRACT.md` and

`docs/ARCHITECTURE.md` §10 row M09; `docs/DECISIONS.md`; this brief and successor prompt refreshes.
Outside the repository: worktrees relocated into `$BATON_HOME/worktrees/`, and the existing
relay's recorded path references. Do not modify Claude's private databases to manufacture grouping.

## 6. Interfaces

- **Introduces:** managed worktree location, guarded relocation and prune with a seven-day
  default; the grouping mechanism supported by the installed CLI, established by observation.
- **Consumes:** `worktree_ensure`, `claude_bg`, the existing dispatch record, Git worktree
  metadata, plan Status and archived completion `merged_as` verified by `lib/inbox.sh`.

## 7. Implementation checklist (ordered)

1. Inventory existing Baton and probe worktrees, branches, HEADs, dirty state and path references.
   Include `Probe07b`, `Probe07g` and `BatonProbe`; identify ownership before moving anything.
2. Read `claude --help` on the host. Test the supported project designation or cwd arrangement
   with one disposable fixture session. Verify both desktop grouping and writes landing in its
   worktree. A changed filesystem root alone does not satisfy grouping.
3. Change creation and reuse to the managed root. Add fixtures for a new dispatch, reuse and
   probe naming; preserve the branch and dispatch commit through relocation.
4. Relocate owned existing worktrees using Git's worktree operations, preserving branches and
   local changes. Account for active working directories and stored path references; do not use
   a blind filesystem move. Record before/after evidence and any unresolved relocation.
5. Restore pruning with all three facts required: milestone done, branch verified merged, grace
   period elapsed. Refuse dirty worktrees; keep every branch. Test the boundary and each refusal,
   including probes. Do not use session resumability or elapsed time alone as permission to prune.
6. Update the standing worktree/retention wording, verify §8, review, fix and close out.

## 8. Fixtures, verification, acceptance

- **No-build:** compare worktree inventories and branch refs before/after; inspect the actual
  `claude --help` output and the selected mechanism.
- **Fixture-run:** managed creation/reuse, relocation preserving branch and dirty changes,
  seven-day boundary, not-done, unmerged, dirty, recent and missing-proof prune refusals;
  probe naming and retention; each twice, then `sh tests/run.sh`.
- **Manual, live:** one disposable probe dispatched through Baton; capture its sidebar project
  grouping and its actual working tree. Capture the existing worktrees' successful relocation.
- **Acceptance:** a dispatch creates no path outside `$BATON_HOME`; existing owned worktrees
  are relocated with branches intact; an eligible close-out older than retention leaves no
  worktree; dirty or unmerged work survives; the dispatched session groups under its project.

## 9. Definition of done and evidence

Handoff per `docs/MILESTONES.md`'s ten-item template, with CLI output, sidebar capture, inventories,
branch hashes and each prune refusal. Do not substitute a proposed grouping flag for a live proof.

## 10. Risks and decisions this milestone settles

- **Grouping may not be exposed.** D-086 found it not settable by a session. Inspect the current
  host and record the result; if no supported approach meets acceptance, report it unfinished.
- **Retention changes a V1 promise.** Seven days after verified close-out replaces indefinite
  worktree retention, independently of transcript retention; record the timestamp used and why.
- **Migration can strand a cwd.** Preserve active work and record how references remain valid.

`Copy-ready session prompt`. M10 is M09's sibling under M17-b, not M09's successor: both were
admitted by M17-b's handover. Do not assume whether M10 has finished at M09's close-out.

At close-out, after recording this milestone as done, re-read the plan's current Status cells,
dependencies and gates. List every direct successor in `eligible[]`, even if it cannot run yet,
and also every other milestone the plan then makes eligible. Derive each disposition at that
moment, with an open gate taking precedence:

- `held` — an open gate holds it; set `held_by` to that gate's exact name.
- `wait` — no open gate holds it and at least one dependency is not done; set `wait_for` to
  the IDs of all dependencies not yet done.
- `run` — every dependency reads done and no open gate holds it.

Use `docs/milestones/<ID>.md` and heading `Copy-ready session prompt` for each entry. Refresh
every listed prompt on main. Compute from the live plan, not an assumed sibling completion

an open gate holds it. Baton initiates successors; this session does not. Explicit naming
prevents `omitted`, while the computed disposition avoids an early `run` disagreement.
