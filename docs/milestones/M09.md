# M09 — Where sessions live, and how they surface

## 1. Identity

- **ID:** M09. **Objective:** create new worktrees under Baton's home, preserve every existing
  recorded session path, and put dispatched sessions under their project in the desktop sidebar.
- **User-visible result:** new worktrees use the managed root; existing branches and dirty work
  survive; sessions remain resumable and appear under their project rather than Other.
- **Size:** Small, about 2–3 hours; medium effort. Host investigation is the uncertain part.

M17-b complete and installed; M10 can run independently. The existing V1 relay is installed. Inspect the
host's `claude --help`, worktree inventory and session rows before choosing a grouping mechanism
or relocating a working directory. This milestone does not depend on M10's new completion fields.

**Kickoff:** M09 is not a root. It depends on M17-b, and M17-b's close-out lists it with disposition
`run`, so the tick admits it — nothing about M09 is hand-dispatched, as SCOPE §7 specifies. M10 is
M09's sibling under the same parent, admitted by the same handover; this M09 session does not start
or restart M10 and does not assume which sibling will finish first.

## 4. Requirements, scope, non-goals

- **Covers:** SCOPE §6 M09 and §8 item 2; REQ-DISPATCH's worktree rules and D-078's
  continuation guarantee.
- **Scope:** `$BATON_HOME/worktrees/<project>/<milestone>` for new attempts without an existing
  owned worktree. Preserve every branch and dirty worktree. Actual desktop grouping remains required.

  **Migrate the legacy sibling worktrees.** Every `<checkout>-<milestone>` sibling — ten of them at
  the time of writing — moves to `$BATON_HOME/worktrees/<project>/<milestone>` with
  `git worktree move`, which rewrites git's administrative files and nothing else. Nothing is
  deleted: branches, commits, uncommitted changes and ignored build products all survive the move.
  This supersedes the earlier scope clause that relocated a session-bearing worktree only after a
  proof, and SCOPE.md §6 M09's matching paragraph, under D-137.

  **Try to migrate losslessly first; the loss is the fallback, not the plan.** The disposable
  fixture this brief has always demanded is still run, and M09 is the first work that can run it,
  because it is a dispatched session and may start a disposable one. It attempts to relocate a
  session-bearing worktree and keep the same session's stop/resume behaviour and correct writes at
  the new path, trying, in order:
  1. any supported relocation the installed CLI actually offers, established by observing
     `claude --help` and the job and session records — **never** by editing them;
  2. a symlink left at the legacy absolute path pointing at the new location, which may satisfy the
     working-directory check. Its cost is honest and must be stated: ten symlinks still occupy ten
     entries in `~/Documents/Apps`, so it buys resume without the tidiness that motivated the move.
     It is a real option only if resume is worth more than a clean listing.

  If a mechanism is proved, migrate losslessly and nothing is given up. If none is proved, migrate
  anyway and record the loss as the owner-accepted cost D-137 defines.

  **It requires the path-resolution change and must not ship without it.** `worktree_ensure` derives
  the path by convention — `we_wt=$(dirname "$we_path")/$(basename "$we_path")-$we_id` at
  lib/dispatch.sh:56 — and never reads the recorded path, so a moved worktree is invisible to it:
  it finds no directory at the sibling path, takes the `git worktree add "$we_wt" "$we_branch"`
  branch at lib/dispatch.sh:69, and git refuses. Measured on git 2.54 in a disposable repository:
  `fatal: '<branch>' is already used by worktree at '<new path>'`, exit 128. That failure reaches
  `dispatch_failed … worktree` (lib/dispatch.sh:322), and two in a row park the lane. Resolve from
  `git worktree list --porcelain`, which `git worktree move` keeps correct, before falling back to
  the managed root for a new attempt.

  **One guard, not D-075's three.** Refuse to move while any live row's `cwd` is that worktree or
  under it. That is the third clause of D-075's *guard 2*, not a guard of its own. D-075's guard 1
  (`Status` reads `done`) and guard 3 (a verified `merged_as` with no newer ending) exist because a
  **delete is irreversible** and a refused question must fail safe; a move loses no bytes, so
  neither is required here. Recorded so a later reader does not restore them by analogy.

  **The dispatch log is not rewritten.** Its `worktree` field records where the worktree was at
  dispatch time, which stays true. Nothing at runtime resolves it as a live path: `lanes_open`
  carries it into the lane at lib/derive.sh:137, and the only consumer is lib/dispatch.sh:341, which
  renders it as a *basename* into another session's "Also in flight" sentence. M09 names that one
  line, because after migration it reads `M28` where it used to read `Reclaim-M28`.

  **Preserve the trail.** Whichever path this takes, the completion evidence records each migrated
  worktree's legacy absolute path beside its milestone, so a person can still find the corresponding
  transcript directory under `~/.claude/projects/` by its slug. Losing a resume button must not also
  lose the way back to the conversation.

  **Two residuals it names rather than solves:** it cannot move its own worktree while running in
  it, and M10 may be running concurrently under the same handover, so a sibling's live worktree is
  left alone. Both stay at their legacy paths, named in the completion evidence. M17's and M17-b's
  worktrees are covered by this same migration, since both lanes close before M09 is admitted; they
  sit at the legacy sibling path through the M17 → M17-b → M09 window, which is accepted and
  recorded rather than worked around by adding worktree work to M17-b, whose scope is one rendering
  layer.
- **Non-goals:** deleting worktrees or branches — relocation is not deletion and is in scope above —
  changing saved transcripts, a new session manager, completion-proof strengthening (M10), non-Git
  projects, or a language rewrite.

  wrong-repository and wrong-branch reuse are refused; no worktree is deleted. Grandfathered

## Completion evidence

### 1. What changed

- **A worktree's location is read from git, not derived from the milestone's name.** `worktree_of`
  asks `git worktree list --porcelain` for the worktree registered on `m<nn>` and falls back to the
  managed root only when the project has none. This is what the milestone actually turned on: with
  the managed root alone, a moved worktree would have been invisible to `worktree_ensure`, which
  would have taken the `worktree add` branch and been refused by git —
  `fatal: '<branch>' is already used by worktree at '<path>'`, exit 128 — reaching
  `dispatch_failed … worktree` and parking the lane on the second try.
- **New worktrees are created under the managed root**, `$BATON_HOME/worktrees/<project>/<milestone>`.
  A target project's parent directory collects nothing.
- **Reuse is verified.** A directory found at the worktree path is refused unless its
  `--git-common-dir` is the checkout's and its `symbolic-ref HEAD` is the milestone's branch. Each
  refusal names both readings and the command to fix it.
- **The tick migrates the legacy siblings**, per project, between steps 6 and 7, with
  `git worktree move` and one guard: refuse while a live row's `cwd` is that worktree or under it.
  One `worktree_moved` event and one line per move; a refusal says nothing.
- **Grouping was measured, not inherited**, and the measurement is that it is not a property of the
  worktree's path. Recorded in D-146 and as the explicit amendment SCOPE §6 M09 and §8 item 2 needed.
