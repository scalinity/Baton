# M15-h — After a replan, the new plan's dispositions win; queued work is not "nothing coming"

## 1. Identity

- **ID:** M15-h. **Objective:** after a replan is adopted, the next work dispatches from the new plan
  rather than from handovers written for the old one; and a milestone blocked on work that is merely
  queued is not treated as blocked on something nothing will deliver.
- **User-visible result:** a replan is followed by the new plan's next milestone starting, with no
  silent stall and no "disagreement" message; a correct plan is never replanned because the cap
  delayed an upstream milestone.
- **Size:** Medium, about 2–3 hours; high effort.

## 4. Requirements, scope, non-goals

**The finding.** A review on 2026-10-01 (findings R07 and R09), confirmed by reading the code:

- **R07.** Adoption reseeds the registration's `start` handover for the new plan, but
  `dispositions_in_force` ranks `start` after every archived handover, so an entry written for the
  old plan still wins. A stale `wait_for` naming a milestone the replan removed stalls silently; a
  stale `run` on a row the new plan makes ineligible raises `disagreement`, a Mac message. The
  existing fixture proves only that the parked lane is redispatched by edit in the same tick, not that
  a new row dispatches from the seed.
- **R09.** `blocker_state` reads "waiting" for both work that is queued (eligible, or in flight, or
  waiting on something that is) and work nothing will deliver. Failing input: cap 1, M01 eligible and
  not yet dispatched, M02 depends on M01, M03 hands over `blocked_by` M02. M03 parks `blocked`, and
  M15-e's request gate passes, so a correct plan is replanned.

**Scope.**

1. **The adopted plan's dispositions win.** After an adoption, the reseeded `start` ranks above every
   archived handover consumed before that adoption, and below any consumed after it. Nothing is
   deleted from the archive.
2. **Queued is not undeliverable.** `blocker_state` distinguishes a blocker that is done, in flight,
   eligible, or waiting on a dependency that is itself in flight, eligible or so waiting (queued) from
   one with no such path (nothing coming). A queued blocker parks as today and is redispatched when it
   lands; only "nothing coming" can satisfy the replan request gate.

**Non-goals.** No change to the validator, to adoption itself, or to how an archived handover is read
for a project that never replanned.

  force and the milestone dispatches; no stall.

  M01 and M02 land, M03 is redispatched.
