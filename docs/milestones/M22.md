# M22 — A ruling continues the session it was given to

## 1. Identity

- **ID:** M22. **Objective:** every resume Baton makes into a session it has just stopped lands on
  that session, not on a copy, so `baton answer` continues the parked session in Claude.app.
- **User-visible result:** after `baton answer`, the parked session reappears in Claude.app under its
  own name and carries on with the ruling; it is not left archived beside a renamed copy.
- **Size:** Small, about 1–2 hours including one live measurement; high effort.

`ladder_position`; this milestone changes `stop_settle` and `resume_session` in the same file, so
merge `main` into the branch at startup and again before the close-out merge, as M19 §10 requires.
M19-b waits on this milestone, because it edits `lib/stops.sh` too.

## 4. Requirements, scope, non-goals

**The measured finding.** On 2026-10-01 two `baton answer` rulings forked instead of continuing: at
22:29:17 for M15-c (session `9e83c239`) and at 22:40:05 for M15-e (`c5070e8b`). Both sessions were
alive and idle, `baton status` listing them in flight with their rows reading `done`, so
`job_of_session` found each job and `resume_session` ran `claude stop <job>` and then
`stop_settle`. The verb printed no `still had a live row after the stop` warning, so `stop_settle`
returned as settled; the flagless `claude --bg --resume` that followed was answered `note: session
9e83c239 is already running in the background, so this started a copy as 9d1c35fd` (and
`c5070e8b` → `a711ee9c`). Claude.app showed each original archived, and each copy carried another
name (`baton m15-c recovery check`) and no sidebar entry. `claude stop --help` on 2.1.286 says
"`claude --resume` works once it is stopped". `stop_settle` treats "no row carrying the session has a
pid" as stopped, and a stopping session's row leaves the listing before its process has exited, so
the resume lands on a live process and forks. Baton's fork handling (D-132) then made the copy carry
the lane, which kept the relay correct but not where the person looks.

**Scope.**

1. **Measure first.** On a fixture project at `~/.baton/m22-probe/`, start one idle `--bg` session
   named `Baton · M22 probe`, then `claude stop <job>` and sample every half second, recording
   verbatim into `~/.baton/m22-probe/README.md`: when the row loses its pid and when it leaves the
   listing; when the process named by the pre-stop row's `pid` exits (`kill -0`); and what a flagless
   `claude --bg --resume <uuid> "<text>"` answers at each of those moments. Ask the person, with
   `AskUserQuestion`, whether the resumed session reappears in Claude.app under its own name. That
   session is the only real session this milestone may start, stop or resume.
2. **Settle on the process.** `stop_settle` waits, within its existing bound, until the process the
   pre-stop row named has exited as well as until no row carries a pid; `resume_session` hands it the
   pid it read with the job. A row that vanished while its process lives is not settled.
3. **Refuse rather than fork.** When the stop does not settle within the bound, `resume_session` does
   not resume: it returns `refused` with the reason that the session's process did not exit. A ruling
   then leaves its park standing and says to answer again, which `lib/answer.sh` already does for a
   refused resume; the ladder and the wait route read it as they read any refused resume.

**Non-goals.** No new way to message a running session: the CLI on this version has none, and Baton
makes no API call. No change to the fork classifier or D-132's compensating stop, which stay for a
fork caused by anything else.

## 8. Fixtures, verification, acceptance

Fixtures use the `claude` shim, a process stub and the `sleep` stub; only §4 item 1 touches a real
session. Run each scenario twice and `sh tests/run.sh`.

- The row leaves the listing while the pre-stop pid lives for three more polls: no resume until it
  exits; then one flagless `--bg --resume <full uuid> "<text>"`, answered as a continuation, and no
  `copy_fork`.
- The pid never exits within the bound: no resume, outcome `refused` with the unsettled reason; under
  `baton answer` the park stands and the message says to answer again.
- A session with no live row before the stop: resumed at once, as today.

## 10. Risks and decisions this milestone settles

A pid is reused by the system eventually; read it once before the stop and settle within the existing
bound, so a reused pid can at worst refuse one resume, never fork one. Record the decision at the next
free D-number read from `main` when it is written. Apply M19 §10, "Main advances while a session
runs", in full: M19 edits the same file now.
