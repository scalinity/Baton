# M03 — The tick under launchd

## 1. Identity

- **ID:** M03. **Objective:** The loop closes. `baton tick` runs the eight steps under the lock
  for every registered project and writes the marker; rows are reconciled; launchd runs it every
  minute through the granted shell; the Mac notification exists. After this milestone Baton
  dispatches Baton without a hand-run verb.
- **User-visible result:** `launchctl` shows `com.baton.tick` loaded; `baton status` prints a last
  tick under a minute old; M04 is dispatched by a tick, not by a person. A crash, a stall, a live
  question, a takeover and a gap each produce their event and their Mac notification.

## 10. Risks and decisions this milestone settles

- **Item 38 is the fact the `~/Documents` decision rests on.** TCC attributes access to the
  responsible process and its children inherit it, but the background service the tick starts
  detaches; whether a detached daemon keeps the attribution is exactly what the prototype did not
  test. If it fails, the fallback is deterministic and named above; do not paper over it.
- **The stall stat must include subagent transcripts** or every `/review-2` close-out reads as a
  stall: the parent sits on one Agent call for twenty minutes while its own file does not move.
- **A sleep is not a crash.** The prototype saw a row byte-identical across a 55 s suspend; the
  two-tick rule guards against a momentary read, not against sleep.
- **The takeover check is trusted only if item 45 passed in M01.** If it did not, log the
  comparison's result without standing off, and say so.
- **The marker's meaning is "a tick completed".** Writing it anywhere but last, after the lock,
  makes the gap report lie.
- **Whether `osascript` needs a fresh Automation grant for System Events under the granted
  shell** is observed on the first notification; the prototype saw no dialog for Messages.
