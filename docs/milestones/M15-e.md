# M15-e — Replan: the request, and the hold while it runs

## 1. Identity

- **ID:** M15-e. **Objective:** make the `replan` disposition act — a standing park of a replan class
  becomes a replan request without a Mac message, and the project's other lanes hold while the plan
  they run under is being replaced.
- **User-visible result:** a milestone that comes back unfinished twice, or one blocked on a
  dependency nothing will ever deliver, produces a new plan instead of a Mac message; nothing else of
  that project is dispatched until the new plan is adopted; and a replan that cannot be made, or
  whose attempts are spent, reaches the person through the park that already stands.
- **Size:** Medium, about 2–3 hours; high effort. Two counted `lib/` files — `lib/tick.sh` and
  `lib/declared.sh` — plus `lib/disposition.sh`, which M15 introduced and which this milestone is free
  to extend as M15-d's brief was, because it is the home of the route family. Recheck that count
  against the then-current interfaces before editing and split rather than cross it.

## 2. Dependencies and entry conditions

M15-d complete and installed. It left the generation path able to replace a plan, and nothing yet
asks it to: `planning_replan <key>` reads `plan_owed.replan` — `{milestone, class, at, detail}`, the
standing park the request names — and every replan rule in `lib/planning.sh` is keyed on it.
`planning_history <key>` is the preserved set (`completion.proved` true on a `consumed` complete) and
the worked set (milestones Baton dispatched). A `plan_generation` event with outcome `requested` is
the request's own record: `planning_attempts` counts the planning lane's dispatches since the newest
one, and `planning_adopt` measures nothing until `planning_landed` reads a proved planning completion consumed after it. Adoption reseeds `start` and
closes the named park with an `edit` resolution, but only while it stands and only when
`disposition_of` assigns its class `replan`. M15-d's five `replan-*` fixtures write those records by
hand; this milestone writes them for real.

M13's admission seam is unchanged and is the one to use: `dispatch_run` re-reads
`claude agents --json` before each dispatch after the first (D-177).

## 4. Requirements, scope, non-goals

- **Scope:** the request, the hold, and the raise without a message — the three things M15-d's
  split moved here (D-200).
- **The request.** From a standing lane park whose class `disposition_of` assigns `replan`
  (`unfinished-twice` and `blocked`, asked of the table and never re-derived), write
  `plan_owed = {reason, owner, replan: {milestone, class, at, detail}}` into the registration and a
  `plan_generation` event with outcome `requested`, through `planning_record`. It is made from the
  standing park rather than from the ending that raised it, so it is idempotent by the park and by
  `plan_owed` standing: a repeated tick makes no second request. A park whose `at` an `adopted`
  event's `replan.at` already names has been answered by that adoption, even if its resolution was
  never written (`onboard_commit` removes `plan_owed` before `planning_close_park` resolves the park,
  so a tick that ends between the two leaves one standing); request nothing for it, or the plan just
  adopted is replaced again. No person approval gate: the
  confirmed intent was the one routine touchpoint.
- **The gate on the request, each refusal named on a line and leaving the park to a person.** (a) A
  confirmed goal, or no request and a line naming `baton onboard <path>` as the verb that supplies
  one. (b) No other open lane of the project, read from `derive_in_flight` — `in_flight` and `no_row`
  both — and no project-scope park. Say in the evidence what this costs: a project that always has a
  sibling running never replans, and that failure is silent. (c) **Every `done` row in the current
  plan is in `planning_history`'s preserved set.** M15-d's validator refuses a `done` Baton did not
  prove, so a plan holding one can never be adopted, and requesting it would spend `planningAttempts`
  sessions on a certain refusal. This is not hypothetical: Baton's own M01 was run by hand and
  every completion before the dispatch baseline existed is recorded unproved (CONTRACT, Baton's side),
  so Baton's own plan fails this gate today, and so will any project onboarded with history. Record
  the count of such rows on the line. (d) **The registration's plan is `native` and registered at
  `docs/MILESTONES.md`** (`PLANNING_PLAN`). M15-d reads a replacement as strictly as a first plan and
  the planning lane's declared scope is that path and `docs/milestones`, so an `adapted` plan — M16
  may register Reclaim that way — or one registered elsewhere can never have a replacement adopted:
  the session is told to write `docs/MILESTONES.md`, the validator finds the registered file first,
  and an edit to that file falls outside the scope its completion is proved against.
- **Not this milestone's, and recorded so nobody assumes it:** M15-d's validator does not refuse a
  replan that drops an inherited gate or `held` cell — it is told and not measured, because Baton
  holds no record of either apart from the document. Measuring it means snapshotting them into
  `plan_owed.replan` at the request and comparing in `lib/planning.sh`, which is a counted file here.
- **The hold, which M15-d measured as necessary rather than tidy.** A replanned project has handovers
  in force, so the plan the planning session merges to `main` is read live by the very next tick,
  adopted or not. `tests/scenarios/replan-preserves-done` freezes the consequence: a refused plan
  that leaves M01 blank meets the old starting handover's `run`, and M01 is dispatched a second time.
  While `planning_replan` answers for a project, step 5 (`dispositions_intersect`) is skipped for it,
  in `tick_run` beside `project_held`. And `edit_reread_check` (`lib/escalate.sh`, called from
  `tick_project`) must not release the replan's park as a person's edit: a real `unfinished-twice`
  park carries a re-read receipt hashing the brief and the work plan, and the planning session's
  merge changes both, so a *refused* replan would free the lane under the refused plan. M15-d's
  fixtures write the park without a receipt for exactly this reason. Settle it at the call site in
  `lib/tick.sh` (for instance, skip the re-read for a project owing a replan; a person's edit is then
  read after adoption) rather than in `lib/escalate.sh`, which would be a third counted file.
- **The raise without a message.** `declared_step`'s two `escalate` calls (`lib/declared.sh`) raise
  the park and send the Mac message in one breath (`escalate` writes the event, then `notify`). When
  the request's gate passes, write the park through a sibling of `record_only` in
  `lib/disposition.sh` — the `escalation` event, its re-read receipt, no message, a `channel` that
  says why — and make the request from it in the same tick. When the gate fails, `escalate` as today:
  the person is told because the route is not available.
- **Silence must not outlive the route.** A park raised silently has told nobody, so when the
  replan's attempts are spent (`plan_generation` `exhausted`, D-167's bound, unchanged) the park's
  own message is delivered then, once. No new escalation class (REQ-ESC-04).
- **Non-goals:** the second judgment role and the `AI-resolvable` route; any change to what
  `record_only` writes or to the four-disposition table; the scope guard (`docs/milestones/M15-c.md`)
  and its drift escalation, which a replan cannot clear (M15-d's `replan-other-park`); a second way
  to compute eligibility; changing `lib/planning.sh`.

## 8. Fixtures, verification, acceptance

Fixture: the request from each of the two classes; a repeated tick making no second request; a
project with no confirmed goal refusing the request and naming `baton onboard`; a sibling lane open
refusing it; a plan with a `done` row Baton never proved refusing it; the project held while the
replan runs, including against a refused plan on `main`; a real re-read receipt not releasing the
park on the planning session's merge; exhaustion delivering the park's message once. Run each twice,
then `sh tests/run.sh`.

Acceptance: a lane whose plan is wrong is replanned without a Mac message; no other lane of the
project is dispatched until adoption; every milestone Baton proved complete is still `done` in the
adopted plan (M15-d); the confirmed intent is unchanged; a replan cannot clear a drift escalation.

proved-history gate each cost, measured; and the test output.

## 10. Risks and decisions this milestone settles

- **A silent park that nobody hears about.** The route has to deliver what it suppressed when it
  cannot finish; exhaustion is that moment.
- **The open-lane gate is conservative.** It is the first thing to revisit if replans never happen.
- **The proved-history gate excludes every project with history from before Baton's proof.** That
  is the price of not believing a plan document's `done`; record the measurement, do not weaken
  M15-d's rule to avoid it.
