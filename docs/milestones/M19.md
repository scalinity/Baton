# M19 — Deliberate stops: pause, resume, and a recovery that cannot stay silent

## 1. Identity

- **ID:** M19. **Objective:** a person can stop a lane on purpose and bring it back, and a recovery
  Baton cannot perform reaches a person instead of failing in stderr.
- **User-visible result:** `baton pause <milestone>` stops the lane's session and `baton status`
  names it as paused, not crashed; `baton resume <milestone>` continues it where it stopped; a crash
  whose job has left the `claude agents` listing is resumed by session id; a refused recovery rung
  becomes a logged event and, after repeated refusal, an escalation.
- **Size:** Medium, about 3–4 hours; high effort.

## 4. Requirements, scope, non-goals

**The measured finding.** On 24 Sep 2026 the person stopped two running lanes, M15-c and M15-d,
with the Stop button in Claude.app because the usage window was exhausted. The two rows left the
listing, so `crash_check` logged `crash_sighting` 1 and 2 at 23:07:53 and 23:08:58. The resume rung
then wrote `resume rung refused: no job identifies session <id> in the listing` to
`~/.baton/launchd.err` on every tick for a week and logged nothing, so `ladder_position` never
counted a failure, never reached `escalate`, and no message was sent. Claude.app had archived both
sessions. Both worktrees held no commits, and a hand `baton dispatch` started attempt 2 on 1 Oct.
Three gaps follow: a deliberate stop is indistinguishable from a crash; the resume rung needs a job
in the listing though a session can be resumed by id (`baton wake` does); a refused rung is silent.

**Scope.**

1. `baton pause <milestone>` (also `project/milestone`): refuse a milestone with no in-flight lane;
   stop the session through the existing stop-and-settle path; write one `pause` event carrying the
   session and attempt; the lane is `paused`. A paused lane is never a crash sighting, never a
   stall or long-running notification, never resumed or redispatched by the ladder, and holds its
   slot under the cap (a pause is not a completion). `baton status` lists it with its pause time.
2. `baton resume <milestone>`: refuse a lane that is not paused; resume the session by id with a
   flagless resume and the continue template (class `paused`); write one `resume` event with kind
   `unpause`; the lane returns to in flight. If the resume is refused, the lane stays paused and the
   refusal is printed and logged.
3. A budget hold or reserve lifting never resumes a paused lane; only `baton resume` does.
4. Crash recovery by session id: when the resume rung finds no job in the listing but the
   transcript exists, resume by id the way `baton wake` reaches a finished session, instead of
   refusing; keep the refusal when the transcript is missing and let the existing redispatch rung
   apply.
5. A refused rung is an event: every refusal of the resume or redispatch rung writes a log event
   with its reason, counted by `ladder_position` as a failure ending, so the ladder reaches
   `escalate` and the escalation reaches a person by the M15 taxonomy.

**Non-goals.** No cancel or abandon verb, no project-level pause, no project deregistration, no
change to the budget pause (M14), no new liveness probe, no model call, no change to what Baton
does when a person stops a session without using `pause` beyond items 4 and 5. Pausing a parked
lane is refused; the park is answered with `baton answer`.

## 10. Risks and decisions this milestone settles

A pause must not be undone by the tick: every automatic start route, resume rung, redispatch and
dispatch pass, reads the paused derivation. Pausing under a running tick must hold the lock the
other verbs hold. Whether a paused lane counts against the cap is settled here as: it does.
A person who stops a session in Claude.app without `pause` is still read as a crash; the fix for
that case is items 4 and 5, not a guess at intent.

**Draft decision (record it, do not paste it blind).** Baton gains `pause` and `resume` verbs, a by-id resume for a crash whose job left the listing, and an event for every refused recovery rung. A paused lane is not a crash, stall or long-running lane, is untouched by the ladder and a lifting hold, and holds its slot under the cap; only `baton resume` returns it. D-101 stands as the record of the gap it closes. Evidence: §4's measured finding.

**Main advances while a session runs.** Other lanes merge into `main` during a dispatch, so the
checkout this session started from is rarely the one it merges into. Two lanes that each mark their
own `docs/MILESTONES.md` row and append to the tail of `docs/DECISIONS.md` conflict on both files
even when their code never meets (measured by merge simulation on 1 Oct 2026, M15-c against M15-d).
So:

- At startup and again before the close-out merge, run `git log --oneline HEAD..main`. If `main`
  moved, merge `main` into this branch in this worktree first, so a conflict is resolved here and
  not in the canonical checkout.
- Resolve a conflict in `docs/MILESTONES.md` by keeping every lane's `done`; in
  `docs/DECISIONS.md` by keeping every row and renumbering this session's own to the next free
  number on `main`, then fixing every reference to the old number in this session's files. Never
  resolve either by taking one side whole, and never use `-X ours` or `-X theirs`.
- Re-read the next free D-number from `main` immediately before writing the row and again if the
  merge conflicts; a number read at startup is stale by close-out.
- Merge only into a clean canonical checkout. If another session has uncommitted work there, do not
  commit, stash or clobber it: wait a bounded time, then write `stopped` and report.
- After the merge, run `sh /Users/danny/Documents/Apps/Baton/tests/run.sh` by absolute path and
  read it to completion; a merge that is textually clean can still break a scenario another lane
  added.
