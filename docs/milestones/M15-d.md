# M15-d — Replan: when the plan is what is wrong

## 1. Identity

- **ID:** M15-d. **Objective:** give the `replan` disposition a route, so that a lane whose plan is
  wrong is replanned from the confirmed goal rather than handed to a person.
- **User-visible result:** a milestone that comes back unfinished twice, or one blocked on a
  dependency nothing will ever deliver, produces a new plan instead of a Mac message — and the
  milestones already marked `done` stay `done`.
- **Size:** Medium, about 3–4 hours; high effort. One counted `lib/` file beyond the one M15
  introduced. Recheck that count against the then-current interfaces before editing, as M15 did,
  and split rather than cross it.

## 2. Dependencies and entry conditions

M15 complete and installed: `disposition_of` assigns `replan` to `unfinished-twice` and to `blocked`,
and nothing acts on it yet. M12 complete and installed: `planning_owed`, `planning_pass`,
`planning_validate`, `planning_adopt` and the `plan_generation` event are the generation path this
milestone routes into, unchanged in shape.

M13 is complete and merged as of 2026-09-19 and **is still not an entry dependency**, because what
it settled is not what replan needs settling. Replan asks for a plan to be rewritten while other
lanes of the same project may be running under the plan it replaces. M13 made that situation
ordinary rather than rare — newly eligible work now runs up to the cap, an independent pair
overlaps, and `dispatch_run` re-reads `claude agents --json` before each dispatch after the first so
a co-dispatched sibling is named in the slot line (D-177) — and it is the admission seam to use. But
it says nothing about a lane whose plan is being replaced underneath it, which is this milestone's
question to answer and not M13's.

So: use `dispatch_run`'s re-read as the admission seam rather than adding a second one, and gate the
request on the project having no other open lane, readable from `derive_in_flight`. That gate is
conservative and it is the thing to revisit first if it proves too strict; say in the evidence what
it cost, because a milestone that never replans because a sibling is always running is the failure
mode nobody would notice.

## 4. Requirements, scope, non-goals

- **Scope:** the `replan` route, end to end — the request, what the generating session is told, what
  the validator will accept back, and the record of the replacement.
- **The obstacle, measured by M15 before this brief was written.** The generation path as M12 left
  it cannot preserve completed work, and it is not close to being able to. `planning_validate`
  raises a defect for **every** row whose `Status` is not blank — "`<plan>` row N marks M05 `done`
  before anybody has done it, and Baton never dispatches a row that is not blank" — with the repair
  "leave every Status cell in `<plan>` blank and commit it on main". `planning_prompt` says the same
  thing twice: in `WHO IS ASKING` it opens "This project is registered with Baton and has no plan
  Baton can read", and in `WHAT THE PLAN MUST SATISFY` it states "Status is blank on every row.
  Nothing is done yet." A replan of a project with `done` rows routed through that path unchanged
  would be refused row by row, and its next attempt's prompt would carry, as a concrete repair, the
  instruction to erase exactly the work this milestone exists to preserve.
- **So the first requirement is a distinction the code does not currently make:** between a `done`
  cell that is a claim nobody has earned — which is what M12 is right to refuse from a plan written
  for a project with no history — and a `done` cell the replan is carrying forward, which Baton can
  check against its own record rather than take the session's word for. The dispatch log knows which
  milestones completed: a `consumed` event with outcome `complete` that Baton proved. That is the
  evidence, and it is Baton's, which is the same principle CONTRACT clause 4 applies to
  `check_result` — a session's word about its own work is what Baton is checking.
- **Which conditions ask for a replan.** `disposition_of` already answers this and must not be
  re-derived: `unfinished-twice` and `blocked`. Both are lane parks, so the request is made from a
  standing park rather than from the ending that raised it, which also makes it idempotent — the
  park is the once-key, exactly as it is for `person_acted`.
- **No person approval gate.** The confirmed intent record was the one routine human touchpoint and
  it has already been taken; asking again for permission to act on its consequences is the review
  that gets rubber-stamped, which `planning_prompt` already tells the generating session not to add.
- **Preserve the park until the plan lands.** The provoking park stands while generation runs, so the
  lane does not redispatch under the plan that was wrong. It is closed by the adoption, and by
  nothing else — which is `park_resolve`'s shape and not a new mechanism.
- **The split, made before implementation (D-200).** The recheck §1 asked for did not hold: the
  whole route needs three counted libraries, measured. `lib/planning.sh` is the generation path
  learning history. `lib/declared.sh` is the raise — both replan classes are parked by `escalate`,
  which writes the event and then always sends the Mac message. `lib/tick.sh` is the hold — a
  replanned project has handovers in force, so the plan the planning session merges to `main` is read
  live before Baton adopts or refuses it, and a real park's re-read receipt would be released by that
  merge as if a person had edited. This milestone keeps the first: the distinction, the prompt, and
  an adoption that closes the park, every rule keyed on `plan_owed.replan`, which nothing writes yet.
  `docs/milestones/M15-e.md` takes the request, the hold and the raise together, because a request
  without the hold dispatches under a plan being replaced. The items of §7 and §8 that moved are
  marked there.
- **Non-goals:** the second judgment role and the `AI-resolvable` route (see §11); host-explained
  gaps (`docs/milestones/M15-b.md`); the scope guard (`docs/milestones/M15-c.md`); replanning a
  project that owes a plan already, which is M12's path and is untouched; any change to what
  `record_only` writes or to the four-disposition table; a second way to compute eligibility.

### 6. Known limitations

- **The refused plan is live on `main`.** A replan session merges before Baton measures, and the
  project has handovers in force, so a refused plan is dispatched from. Frozen, labelled, in
  `replan-preserves-done` (M01 dispatched again from a blanked row) and `replan-rules` (an `omitted`
  park — a Mac message — on a refused plan's new row). M15-e's hold removes both.
- **A real park would be released by the planning session's merge.** Both replan classes carry a
  re-read receipt hashing the brief and the work plan, and `edit_reread_check` reads a changed hash
  as a person's edit. Every fixture park here is written without one, and the acceptance clause says
  so; M15-e guards it at its call site in `lib/tick.sh`.
- **Unproved history blocks adoption, by design.** A completion recorded unproved — before the
  dispatch baseline, or of a milestone Baton did not dispatch — cannot be told from a claim, so a
  plan carrying it as `done` is refused. Baton's own plan is such a plan (M01 was run by hand). M15-e
  declines to request a replan that would be refused for it.
- **Only a native plan at `docs/MILESTONES.md` can be replaced.** An `adapted` registration, or one
  whose plan lives elsewhere, is read as strictly as a first plan and refused; M15-e declines it.
- **Keeping inherited gates and `held` cells is told, not measured** — Baton holds no record of
  either apart from the document being replaced.
- **A proved milestone a person removed from the plan is required back**, because the preserved set
  is the whole log's.
- **Two attempt numbers in one prompt.** The replan prompt numbers its generation ("This is attempt
  2"); the slot paragraph `lib/dispatch.sh` composes says the planning lane's lifetime count ("attempt
  5 at this milestone"), which is true of the lane id. Aligning them is a counted file.
- `lib/planning.sh` is 1,340 lines. It was 989 before this milestone and the codebase has carried
  libraries past a few hundred lines since M11 without invoking D-005; nothing here needed a structure
  `jq` cannot express.
