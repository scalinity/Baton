# M07-d — A handover is acted on once

## 1. Identity

- **ID:** M07-d. **Objective:** a handover delivered twice — the same session's same artifact
  written into the inbox again after the tick consumed it — is recognised and changes nothing, so a
  repeated file can never put an older word back in force or start a session a newer handover held
  back. Baton's last milestone before Reclaim, because Reclaim's lanes run in parallel.
- **User-visible result:** a re-delivered handover is archived with a line and an event saying it
  repeats one already acted on; no disposition, dispatch, park or resolution follows from it.

## 4. Requirements, scope, non-goals

- **Covers:** INV-06 stated for a handover and not only for a file; REQ-ARTIFACT's consumption rule
  for a repeat; derivation 4 (`derive_consumed`) and `dispositions_in_force` ranking by what was
  written rather than by when it was consumed.
- **Scope:** the repeat test at the consume; what a repeat writes; the ranking; fixtures.
- **Non-goals:** refusing a session's second, different artifact — a session that wrote `stopped`
  and later `complete` has two handovers, not one twice; anything Reclaim.

## 7. Implementation checklist (ordered)

1. Fixtures first, each shown failing on the code as it stands: (a) a `complete` handover consumed,
   then the identical file delivered again — today it is consumed a second time into a second
   archive entry; (b) handover A lists milestone X `run`, a newer handover B lists X `held` or
   `wait`, then A is delivered again — today A becomes the newest handover in force and X is
   dispatched against B's word; (c) the same session's two different artifacts, which stay two.
2. The repeat test at the consume: what makes an artifact the same handover — the same project,
   milestone, session, outcome and `written_at`, or the file's bytes — settled with the reason, and
   what a repeat writes (archived beside the first with an event that names it, or moved to
   `rejected/` with a rule), settled against REQ-ARTIFACT's "never skipped, always recorded".
3. The ranking: `dispositions_in_force` and `cap_order` order handovers by what was written, or
   skip repeats, so that no delivery order can put an older handover in force.
4. The fixtures, twice each; `sh tests/run.sh`, `/review-2`, `/address`, completion evidence, the
   handover.

## 8. Fixtures, verification, acceptance

- **Fixture-run:** every scenario in §7 item 1, twice.
- **Acceptance:** a repeated handover changes no disposition and dispatches nothing; two different
  handovers from one session are both acted on.

## 9. Definition of done and evidence

Handoff per template with the fixtures' failing output before the change and passing output after.

## 10. Risks and decisions this milestone settles

- **The hazard, traced.** `dispositions_in_force` (`lib/candidates.sh`) ranks archived handovers by
  consume order: `derive_consumed`'s list, reversed, rank 0 the newest consumed. A handover consumed
  again is therefore the newest handover in force for every milestone it lists, over any handover
  written after it. With parallel lanes, a repeated older handover that says `run` for a milestone a
  newer one said `wait` or `held` dispatches it early — a session started that the plan's own last
  word held back. Lanes already open or `done` are not candidates, which is what kept M07's own
  instance harmless.
- **What happened once.** M05's session wrote its handover again after the tick had consumed it (its
  close-out says to print again if anything lands after); the identical file was consumed at 15:32:12
  on 2026-09-12 into a second archive entry, with M06 already in flight (M07 completion evidence §6).
