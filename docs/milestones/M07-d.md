# M07-d — A handover is acted on once

## 1. Identity

- **ID:** M07-d. **Objective:** a handover delivered twice — the same session's same artifact
  written into the inbox again after the tick consumed it — is recognised and changes nothing, so a
  repeated file can never put an older word back in force or start a session a newer handover held
  back. Baton's last milestone before Reclaim, because Reclaim's lanes run in parallel.
- **User-visible result:** a re-delivered handover is archived with a line and an event saying it
  repeats one already acted on; no disposition, dispatch, park or resolution follows from it.

## 10. Risks and decisions this milestone settles

- **The hazard, traced.** `dispositions_in_force` (`lib/candidates.sh`) ranks archived handovers by
  consume order: `derive_consumed`'s list, reversed, rank 0 the newest consumed. A handover consumed
  again is therefore the newest handover in force for every milestone it lists, over any handover
  written after it. With parallel lanes, a repeated older handover that says `run` for a milestone a
  newer one said `wait` or `held` dispatches it early — a session started that the plan's own last
  word held back. Lanes already open or `done` are not candidates, which is what kept M07's own
  instance harmless.
- **What happened once.** M05's session wrote its handover again after the tick had consumed it (its
  close-out says to print again if anything lands after); the identical file was consumed at 15:32:12
  on 2026-09-12 into a second archive entry, with M06 already in flight (M07 completion evidence §6).

### The two settlements

- **What makes a repeat (D-095).** A file repeats a handover when it holds the same JSON value — keys
  sorted, so spacing and key order do not count, and `written_at` kept — as an archived copy of a `consumed`
  handover for the same milestone and session: its first file, or an earlier repeat's. Not the bytes,
  because the Stop gate's printed fallback writes the fence's text, not the session's file. Not the tuple
  of project, milestone, session, outcome and `written_at`, because a file changed under the same
  `written_at` would lose what changed. `written_at` stays because two Stop gate `no-handover` endings for
  one session can carry the same words and differ only there, and the ladder counts each.
- **What a repeat writes (D-095).** The move into `archive/` under the usual consumed-at name, one
  `repeated` event (`outcome`, `archive`, `repeats`) under the first handover's envelope, one line. No
  check, stop, route, park, notification or `consumed` event; not `rejected/`, because a rejection parks a
  lane over a file that asks nothing. Every rule that acts on an ending reads `consumed`, so none needed a
  change.
- **The ranking (D-096).** Unchanged in code: `dispositions_in_force` ranks derivation 4's `consumed` list,
  reversed, and `cap_order` reads that rank; a repeat has no `consumed` event, so no delivery of it can
  stand in front of a newer handover. `written_at` was not used (the contract never reads it for order, and
  it is wrong for the ordinary parallel close-out) nor the ancestry of `merged_as` (it cannot order a branch
  commit another lane's merge lacks, and costs a git read of `main` per project per tick).

### 6. Known limitations

- **A late, different handover still ranks by consume order** (D-096): lane A merges, lane B merges with A's
  merge in view, A's slower standing check writes A's artifact last, and A's older word is in force for any
  milestone both list. The plan's gates, `wait`'s dependency on `done` and the `disagreement` park bound
  the harm. Reversal condition recorded in D-096.
- **A handover whose every archived copy has been moved away is not recognised**, and a later delivery of
  it is consumed again (D-095, `consume-repeat-archive-gone`).
- **The log's existing duplicate** — M05's second `consumed` event of 2026-09-12 — stays in the log and in
  `consumed`; every handover consumed after it ranks above it, so it holds nothing back.
- **This session inherited `BATON_HOME=/Users/danny/.baton/m03-probe/home`** from the background service
  (D-091); the install names its home.
