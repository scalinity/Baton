# M12 — Plan generation from a repository

## 1. Identity

- **ID:** M12. **Objective:** turn the confirmed goal and a repository with no usable plan into
  a dispatchable milestone plan and self-contained briefs through a Claude Code session.
- **User-visible result:** onboarding a repository with no `docs/MILESTONES.md` produces a
  plan whose first milestone dispatches and completes, without a plan-approval conversation.
- **Size:** Large, about 5–7 hours; high effort. The cold end-to-end path is the substantial proof.

## 2. Dependencies and entry conditions

M11 complete and installed. Onboarding already resolves a Git project, derives its permissions,
confirms intent once and stores `goal`, `plan_format` and `onboarded_at` in its registration.
It adapts usable plans and identifies the no-usable-plan case; M12 implements that missing path.
Managed worktrees/grouping and baseline/scoped-change/Baton-check completion proof are installed.

## 3. Required reading

`CLAUDE.md`; `CONTEXT.md`; `CONTRACT.md`; `docs/v1.1/SCOPE.md` in full, especially §5 and §6 M12;
`docs/MILESTONES.md`; `docs/v2/01-findings.md` MILESTONE FORMAT in full; `docs/milestones/M07-d.md`
as the real format exemplar; `docs/SPEC.md` §2.1, §2.2, §2.6–2.8; `docs/ARCHITECTURE.md` §3,
§4.1–4.3, §7, §10; M11 completion evidence and its decision entries; current onboarding code,
`lib/plan.sh`, `lib/dispatch.sh`, `lib/inbox.sh`, `lib/candidates.sh`.

## 4. Requirements, scope, non-goals

- **Covers:** SCOPE §6 M12 and §8 items 1 and 7; extends REQ-CONTRACT and REQ-PLAN for generated plans.
- **Scope:** dispatch a cold Claude Code planning session using the stored confirmed goal and
  repository evidence; produce one plan graph, conforming briefs and initial handover; validate
  output before admission; run the first generated milestone through verified completion.
- **Non-goals:** approving the plan again, managed review sessions, a generic agent framework,
  direct model APIs, implementing the scope guard (M15-c) or completing a whole chain here (M13).

## 5. Expected files (proposed)

New `lib/planning.sh` and a repository-local planning prompt/template if needed; narrow changes
to the M11 onboarding module and `lib/dispatch.sh`; `tests/scenarios/plan-generate-*`;

## 6. Interfaces

- **Introduces:** the no-plan generation path, its repository/goal prompt, validation of its
  returned plan and briefs, and `plan_format: generated` on successful adoption.
- **Consumes:** M11's stored goal and no-plan result; `claude_bg <worktree> <name> <model>
  <effort> <settings> <prompt>`; existing hooks, mailbox and completion checks; plan parsing and
  candidate selection. Model judgement runs in a CLI session, never inline in the tick.

## 7. Implementation checklist (ordered)

1. Trace M11's no-plan path and add fixtures for absent/unusable plans, stored goal missing,
   and a resumable generation attempt. Do not reconfirm a goal already confirmed.
2. Write the planning prompt from repository evidence and the stored goal. Require the exact
   11 numbered sections and three unnumbered headings from MILESTONE FORMAT; each generated
   brief must contain its own context, Size, scope, acceptance and seven-part kickoff block.
3. Require token-only plan cells per CONTRACT clause 2, blank pending Status, real dependencies
   and no new approval gate. Require exact Completion evidence/Copy-ready session prompt
   headings, the verbatim slot paragraph, close-out proof and explicitly named successors.
4. Dispatch the planning session through the existing subscription CLI seam and hooks. Adopt
   only output that parses and conforms; return correctable defects to the generation path with
   concrete diagnostics. Preserve partial work on a resume instead of generating a second graph.
5. Publish the generated plan/briefs through the target's normal Git close-out and seed the
   initial runnable names automatically. Expose the adopted-plan boundary so M15-c can later
   check it against the goal; do not implement that guard in this milestone.
6. Onboard a disposable repository lacking `docs/MILESTONES.md`, confirm intent once, and
   observe a cold generated milestone dispatch and complete with Baton-recorded proof. The
   planning session must not perform that milestone itself.
7. Run §8, document the delivered interfaces, review, fix and close out.

**Natural split point after item 4.** Generation and conformance validation are coherent;
adoption, automatic seed and the live first-completion proof are the remainder. Record the split
under the plan rule; M12 is unfinished until both halves' acceptance holds.

## 8. Fixtures, verification, acceptance

- **Fixture-run:** missing plan, unusable plan, missing goal, correct generation, invalid cells,
  missing headings/slot, missing successor names, partial generation resume and duplicate
  completion; each twice, then `sh tests/run.sh`.
- **Manual, live:** a disposable owned Git repository with no plan, one intent confirmation,
  one planning session and a separate fresh milestone session; capture the latter's completion.
- **Acceptance:** the repository is onboarded, generates a conforming plan and briefs, and its
  first milestone dispatches and completes. No human plan review or hand-written seed is needed;
  all judgement and work stay on the subscription CLI.

## 9. Definition of done and evidence

Ten-item handoff with the repository's initial no-plan state, stored goal, generated files,
conformance output, session IDs and prompt sidecars, and accepted first-milestone proof. Identify
the planning and implementation sessions separately so one cannot masquerade as the other.

## 10. Risks and decisions this milestone settles

- **A fresh session cannot inherit a sibling.** The generation prompt must require repository
  paths and relevant facts in every brief, not “continue the previous plan” instructions.
- **Bootstrap can stall on omissions.** The initial handover and each generated close-out must
  name successors; plan eligibility alone is not a `run` disposition in the current relay.
- **Generation is not an approval loop.** The stored goal is the authority; validation fixes
  malformed output. Scope drift detection belongs to M15-c, not an invented person gate here.

Apply `CONTRACT.md` clause 3(c) to every refresh below: run `baton status` and check the
dispatch log for open lanes, including lanes absent from status; status also lists open parks. Refresh only a listed
milestone with neither an open lane nor an open park; still name every eligible milestone with its correct disposition.

The direct successors in the current graph are **M13 and M15**, paths `docs/milestones/M13.md`
and `docs/milestones/M15.md`, heading `Copy-ready session prompt`.

At close-out, after recording this milestone as done, re-read the plan's current Status cells,
dependencies and gates. List every direct successor in `eligible[]`, even if it cannot run yet,
and also every other milestone the plan then makes eligible. Derive each disposition at that
moment, with an open gate taking precedence:

- `held` — an open gate holds it; set `held_by` to that gate's exact name.
- `wait` — no open gate holds it and at least one dependency is not done; set `wait_for` to
  the IDs of all dependencies not yet done.
- `run` — every dependency reads done and no open gate holds it.

Use `docs/milestones/<ID>.md` and heading `Copy-ready session prompt` for each entry. Refresh
on main only listed prompts whose milestones have neither an open lane nor an open park with the goal/plan-adoption and generation-resume interfaces.
Compute from the live plan, not a predetermined disposition; never change dependencies or add
a gate to obtain it. M15's replan disposition uses M13's autonomous continuation when available,
but M13 is not an added entry dependency for M15. Baton initiates successors; this session does not.

## Completion evidence


### 1. What changed

- **`lib/planning.sh` is new and is the whole generation path.** A registered project whose
  registration carries `plan_owed` gets one planning session dispatched for it, on the reserved
  milestone id `M00-plan`; the session reads the repository and the confirmed intent record and
  writes the project's plan document, one brief per milestone and, where it is missing, the line in
  `CLAUDE.md` that names the plan file. A later tick measures what it wrote and, when every
  measurement holds, adopts it.
- **The pass runs beside the self-check and before it.** A project that owes a plan is exactly a
  project the self-check fails and skips for the rest of the tick (it parks `plan-unreadable`), so a
  pass placed after it would never run. Placed before it, a plan adopted in the pass is read by the
  self-check on the next line and its park is closed by the ordinary `park_resolve`, in one tick.
- **Adoption goes through onboarding's own seeding path**, `onboard_commit` with the seed, so
  `plan_format`, the plan pointer and `plan_owed` are brought up to what the plan says and the
  starting handover is derived once by `onboard_start`. Nothing computes eligibility a second way.
- **The plan is measured, not hoped.** It must read `native`; its graph must hold (every `Status`
  blank, every dependency a row in the same table, no self-dependency, the reserved id unused, no
  uncleared gate, at least one milestone eligible); `CLAUDE.md` must name it; and every brief must
  pass the dispatch preconditions `baton plan` already reports plus five questions only a generated
  brief is asked — the eleven numbered sections and three unnumbered headings, an empty
  `## Completion evidence`, a `## 5.` naming a path between backticks, a `## 11.` naming every
  successor, a `Size` in `## 1.`, and a kickoff prompt carrying the slot paragraph verbatim and all
  seven parts. Every defect carries its repair; all of them are reported in one pass; they travel
  into the next attempt's prompt, which repairs the plan in place rather than writing a second graph.
- **The planning lane is an ordinary lane.** `dispatch_one` takes it through the same worktree,
  settings file, launch, cleanup budget, `dispatch` event and five printed lines, branching only on
  model and effort, on preconditions and on the prompt. Its completion is proved the same way, and
  `completion_scope_patterns` answers its declared scope, which is Baton's own text because the
  project had no briefs to declare one.
- **One pre-existing race was fixed rather than recorded** (D-172). `completion-timed-out` failed
  once in M12's own suite run, under the load of two lanes and several sessions, and passed three
  times in a row alone: the deadline's kill can land between `>` creating `output.txt.exit.tmp` and
  the rename that publishes it, leaving the file in the evidence directory. Nothing reads it and the
  next run sweeps it, so the only cost was a **non-deterministic standing check** — and that is the
  one place non-determinism is expensive, because the standing check is what every completion is
  proved against, Baton runs it on `main` under exactly the load Baton creates, and a flake there
  parks a project `main-broken` for a milestone that did nothing wrong. The deadline now sweeps it.

### 5. Checks not run, and why

- No scenario asserts what happens when the planning session is stopped by a usage limit. The
  protection is the existing one and is reasoned rather than measured here: a wait on the planning

  establishes about a real session is live-only by construction.

### 6. Known limitations

- **The planning lane gets no ladder, no waits and no crash or stall reconciliation.** Those passes
  live in `tick_project`, which runs only for projects that pass the self-check, and a project that
  owes a plan is one that does not. A planning session that ends without a handover therefore
  recovers by a fresh attempt on the next tick rather than by a resume — which the prompt is written
  for, since it tells the session to repair the plan in place — bounded by `planningAttempts` and
  withheld while a model hold stands. Running steps 3 and 4 for a project that owes a plan would fix
  it properly and is a wider change than this milestone; it is not attempted here.
- **Validation re-runs every tick while a plan is owed and a plan exists**, including after the
  attempt bound is spent, because a plan a person repairs by hand must still be picked up. The cost
  is the dispatch preconditions for each milestone in the plan, once a minute, for a project nobody
  has repaired.
- **`plan_owed.defects` is not bounded by count.** Each defect is cut at 300 characters where it
  reaches the prompt and the event; the registration keeps them whole, which is Baton's own file.
- **The slot line's attempt-2 sentence mentions a brief the planning lane does not have**, and in
  one edge case the "also in flight" list could name `docs/milestones/M00-plan.md`. Both are
  cosmetic strings in a prompt whose own text is unambiguous about what to do, and both live in
  `lib/templates.sh`, a fifth counted file against a milestone already over the split rule's count.
- **Validation re-runs every tick while a plan is owed and a plan exists.** Measured rather than
  guessed: eleven `dispatch_preconditions` passes took 2 seconds on this Mac, so an eleven-milestone
  plan costs about two seconds of a sixty-second tick, and only for a project nobody has repaired.

- **Four `lib/` files change beyond the one introduced**, where the split rule triggers above two.

- **A generated plan must read `native`** (D-166), which is stricter than the reader is for a plan

### 4c. The review, and what it changed

`/review-2` ran two agents on Fable — a debugger and a code-auditor — over `lib/planning.sh` and
the changed hunks of the three seam files. Both independently found the same critical defect, which
a hand pass over `dispatch_try`, `escalate` and `attempt_of` then confirmed, and it was real:

**The planning candidate bypassed the lane-scope park filter.** `dispositions_intersect` drops a
candidate whose lane carries a lane-scope park, which is what makes `dispatch_try`'s own sentence
true — "the park is then what stops the retry". The planning lane never reaches that function,
because a project that owes a plan fails the self-check. With a permanent precondition failure —
exactly `plan-generate-no-rail` — the second tick escalated `dispatch-failed` and notified, and
every tick after that re-dispatched, re-failed and escalated **again**, because `dispatch_try` has
no once-key and `escalate` de-duplicates nothing: a Mac message a minute, indefinitely, about a
condition the person had already been told about. The attempt bound did not catch it, because a
dispatch that produces no session writes `dispatch_failed` and not `dispatch`, so `attempt_of`
never moved. And nothing could have released the park: `edit_reread_check` runs only inside
`tick_project`, which this project never reaches.

Fixed in both halves and both are fixtures now (D-169): a lane park withholds the candidate
(`plan-generate-lane-parked` — two ticks, no dispatch, no second escalation), and a
`dispatch-failed` park is released by the pass that would otherwise re-fail, once the preconditions
hold again (`plan-generate-lane-unparked` — the rail restored, the park resolved, the dispatch
made). That release is the same act `park_resolve` performs for the self-check's own parks: the
condition is one Baton can read for itself.

Also fixed from the review:

- `planning_preconditions` re-implemented two rules `dispatch_preconditions` already has, one of
  them splicing the checkout path into a jq program as source text rather than passing it as data
  (CWE-116). It now runs the one pass and keeps the two checks that are this lane's, which deletes
  both the duplication and the injection (D-170).
- The prompt hard-coded the model alias list, so a renamed alias would have had a plan refused for
  a model the prompt told the session to use. It reads `config.json` now, and the id rule was
  corrected to what `parse_id` accepts (D-171).
- The verbatim-slot check did not require the blank line after the paragraph. `slot_line` swallows
  every non-blank line that follows, so a brief whose part 3 began on the next line would have lost
  its whole STARTUP ORDER at dispatch, silently, and passed validation.
- `planningAttempts` was compared without being validated as a number, and a non-numeric value made
  the bound vanish rather than fall back.
- The `exhausted` event carried `plan_owed.reason` uncut; a large enough defect could have pushed
  the line past `log_event`'s 4 KB refusal, which would have left the exhaustion unrecorded and
