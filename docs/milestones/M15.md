# M15 — The escalation taxonomy

## 1. Identity

- **ID:** M15. **Objective:** resolve what Baton can resolve itself and replan when the plan is wrong.
- **User-visible result:** routine ambiguity no longer produces a Mac question; credentials,
  access and external facts still reach the person. Every class has an explicit disposition.
- **Size:** Medium, about 3–4 hours; high effort. Before implementation, the former Large
  6–8-hour brief is split: M15 owns taxonomy, AI/replan routing and L33; M15-b owns host-explained
  gaps and wake reconciliation; M15-c owns the independent goal guard. Nothing is implemented
  by this planning edit. Each implementation must recheck the plan's two-existing-library limit
  against the then-current M12 interfaces and split further before crossing it.

## 4. Requirements, scope, non-goals

- **Precondition failures:** classify known dispatch-precondition failures, including whether they should escalate on the first occurrence; M17 deliberately retains `dispatch_try`'s existing retry-then-escalate bound.
- **Covers:** SCOPE §6 M15's disposition routing and L33. The original guard acceptance moves
  to M15-c; the host finding below is implemented in M15-b.
- **Scope:** four dispositions: `AI-resolvable`, `human-required`, `replan`, and
  `HOST-EXPLAINED`. The fourth means the condition is real and correctly detected, the host
  explains it, and no action exists: record the event; send no notification. It is neither an
  AI task nor a human park. Preserve lane/project scope independently of disposition.
- **Non-goals:** implementing M15-b or M15-c in this session, deleting existing machinery,
  weakening deny rules, inferring credentials/external facts, direct API calls or a new framework.

### Verified finding — 2026-09-17 (planning evidence, not implementation acceptance)

The person reported seven `Baton · gap` messages (3m, 9m, 41m, 1h09m, 1h17m, 1h26m,
1h33m), each saying “and a lane was open through it,” with no understandable action.
Inspection found:

- `derive_gap` reports at **age >= 2 × BATON_TICK_SECONDS**, with a lane in flight, waiting
  or parked, including an ending after the marker. `gap_check` tests prior `notification`
  events with class `gap` and **key equal to the marker value**. ARCHITECTURE derivation 15
  agrees. These are correct missed-tick detection and deduplication, not cause attribution.
- `caffeinate_rearm` rearms idle-sleep assertions for current pids and bounded waits. Its comment
  and REQ-SETUP-07 explicitly say `caffeinate -i` cannot prevent lid-close sleep and Baton cannot
  lift this. No proposal here changes that hardware constraint.
- The real `/Users/danny/.baton/log.jsonl` had **16**, not seven, gap events dated September 17
  at inspection (through 18:11:24 EDT). All seven reported durations occur; 41m occurs more
  than once. The seven visible messages are not the complete event count. Notification delivery
  or which messages the person saw was not independently reconstructed.
- `/usr/bin/pmset -g log` exposes `YYYY-MM-DD HH:MM:SS ±HHMM` timestamps and actual `Sleep`,
  `DarkWake`, and `Wake` transitions. `Wake Requests` are scheduled requests, not wakes.
  A single capture had 960 transition lines (958 distinct timestamp/type records), reaching
  from September 11 through September 17. Native `/bin/date -j -f '%Y-%m-%d %H:%M:%S %z'`
  parsed their timestamps. Sort and deduplicate evidence; never count duplicated intervals twice.
- A temporary `launchctl submit` job using **Baton's installed shell**
  `/Users/danny/.baton/bin/sh` ran `/usr/bin/pmset -g log` as uid 501 with parent pid 1,
  exit 0 and empty stderr, without sudo or a new permission grant. The temporary job was removed;
  the real tick agent was not changed or invoked. This verifies the current user's LaunchAgent
  context, not every macOS version or a system daemon. Probe output is in
  `/tmp/baton-sleep-inspect.SJYDw2/` (temporary, not a durable fixture dependency).
- The host was **not continuously asleep for each whole marker-to-read interval**. Short dark
  wakes interrupt sleep and Baton sometimes ticks during them. Pairing Sleep with the next
  Wake **or DarkWake**, all 16 measured gaps were mostly sleep; the longest continuous awake
  remainder was 56 seconds. Examples below use the actual measured endpoint
  `epoch(marker) + gap_seconds`, not event-write time. The 1h09m event was written at 16:37:50
  but measured 4,152 seconds from 15:11:51, ending at 16:21:03; a later event timestamp must
  not silently enlarge the interval being explained.

**Feasibility:** affirmative, for retained, complete, parseable host history in this measured
LaunchAgent context. It is evidence for a conservative explanation, not a guarantee of a complete
history or proof of launchd health. Missing history, parse errors, read failure, contradictory
transitions, reboot boundaries or clock discontinuities cannot establish sleep coverage. They
must remain unknown and must not silently suppress a gap. M15-b defines that fallback and the
fixture boundary; no privileged helper, power assertion workaround or new liveness test is needed.

**Two other corrections matter to the design.** `status_render` currently re-derives the *active*
gap from `last-tick`; it does not show a historical gap after the marker advances. Therefore
preserving the log alone does not satisfy “baton status still shows it”: M15-b must render the
recorded latest gap, including a silent one. Also D-078 is evidence of a **service restart plus
missing working directory**, not evidence that sleep kills sessions. The current daemon log
confirms the 2.1.270 restart at 2026-09-12T19:48:32Z and M04/M05 settling at 19:48:47Z as
`(crashed): working directory no longer exists or is not accessible`. D-078 records Claude.app's
“not connected” and unsendable-message result; that UI state was not re-enacted in this inspection.

### Required behavior carried into M15-b

A host-explained gap retains its event, duration, marker key and status visibility but emits no
Mac message. A gap with complete history reporting no explanatory sleep is **UNEXPLAINED** and
still notifies: unloaded launchd, a stuck lock or a crashing tick are possible causes to investigate,
not diagnoses inferred from the gap alone. Unknown host evidence also retains the existing gap
notification, explicitly marked unknown rather than falsely claiming “no sleep.”

On waking, reconcile open lanes using the existing row, transcript, inbox and ending checks.
Sleep, unchanged rows/transcripts and Claude.app connectivity alone are not death evidence.
A confirmed dead session takes the existing recovery ladder; only an actionable unresolved
failure reaches the person. M15-b specifies the two-tick confirmation and fixture cases.
